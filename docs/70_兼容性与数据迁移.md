## 一、支持矩阵

| 维度 | 状态 | 说明 |
|---|---|---|
| Windows 10 / 11 | ✅ 主支持 | GUI、电脑控制、截图、剪贴板、DPAPI 等按 Windows 桌面设计 |
| Windows Server | ⚠️ 部分可用 | 可运行，但不是主要验证目标；CI 允许 `--allow-server` |
| Windows 7 / 8 | ❌ 不建议 | 旧 API、Qt 与运行库均未做保证 |
| macOS / Linux | ❌ 桌面能力不支持 | 聊天和部分文件功能可能可用；桌面 Agent 核心能力不可用 |
| Python 3.10 | ✅ CI 目标 | 代码语法与依赖目标版本 |
| Python 3.11 | ✅ CI 目标 | 代码语法与依赖目标版本 |
| Python 3.12 | ✅ 当前实测 + CI | 当前开发机实测环境 |
| Python 3.9 及以下 | ❌ 不支持 | 使用 `str | None`、`dict[str, ...]` 等 3.10+ 语法 |
| Python 3.13 | ❌ 未验证 | PyQt5 与部分二进制依赖可能不兼容 |
| 旧公共导入路径 | ✅ 兼容 | 拆分后的门面 re-export 仍保留 |
| 旧配置 | ✅ 大部分兼容 | 默认字段补齐、类型回退、新字段合并 |
| 旧数据 | ✅ v0→v1→v2 | 自动备份后逐级迁移；坏行保留 sidecar |
| 插件 | ✅ API v1.0 | RSA 签名 + 公共 API 边界检查 |

### CI 兼容矩阵

`.github/workflows/compat-matrix.yml` 会跑：

```text
windows-2022 / Python 3.10
windows-2022 / Python 3.11
windows-2022 / Python 3.12
windows-latest / Python 3.10
windows-latest / Python 3.11
windows-latest / Python 3.12
```

每一步包含：依赖安装、插件清单生成、运行环境检查、语法编译、
数据迁移 dry-run、插件 API 检查、核心兼容测试。矩阵只验证 Windows
和受支持 Python，不把 macOS/Linux 的桌面能力误报为支持。


## 二、数据版本与迁移

### 2.1 版本登记

`data/_schema.json` 记录每个受关注数据文件的版本：

```json
{
  "data_schema": 2,
  "files": {
    "memory_cards.jsonl": 2,
    "personality.json": 2,
    "chats.db": 2
  }
}
```

缺失登记项按 **v0 旧数据**处理，不会直接伪装成 v2。

### 2.2 逐级迁移

`core/data_migrations.py` 为每个文件维护 `{源版本: 迁移函数}`：

```text
v0 -> v1   旧格式归一化（字符串/数组/旧键名/SQLite meta）
v1 -> v2   补齐当前字段、SQLite 列、schema_version、加密/默认配置
```

规则：

1. 只按版本递增执行，不允许跳步；
2. 迁移前备份到 `data/_migrations/backup_<时间>/`；
3. JSON/JSONL 用临时文件 + 原子替换；
4. JSONL 坏行原文写入 `.bad_lines`，不静默删除；
5. SQLite 使用事务与 `x6_meta` 版本表；
6. 单个文件失败时报告错误，不覆盖原文件。

### 2.3 命令

```powershell
# 只预演，不改文件
py -3 tools/migrate_data.py --dry-run --json

# 真正执行
py -3 tools/migrate_data.py

# 界面入口
设置 -> 系统 -> 深度自检
```

迁移报告包含 `migrated`、`skipped`、`errors`、`backups`；
`trunk` 启动时也会自动执行，并把结果写进运行日志。

### 2.4 仍有限制

- v0/v1 的历史格式只能做可解释的归一化，无法保证所有私有字段无损；
- 加密旧数据依赖原机器 DPAPI 或原密码，换机后仍需用户提供密码；
- SQLite 只能补齐已知列，未知表结构保留不动；
- 迁移不是数据修复器，坏行会保留但需要人工判断。


## 三、插件公共 API v1.0

### 3.1 版本声明

- 代码常量：`core/plugin_api.py::PLUGIN_API_VERSION = "1.0"`；
  `modules.base.PLUGIN_API_VERSION` 也暴露同一个值，方便插件作者读取。
- 清单字段：`modules_repo/manifest.json` 每条必须写 `api_version: "1.0"`。
- 官方随包条目写 `first_party: true`；第三方插件不得伪造官方身份。
- 当前只接受 `SUPPORTED_PLUGIN_API = {"1.0"}`。
- 旧清单没有 `api_version` 时按 legacy 兼容模式给出 warning；新发布必须补上。

### 3.2 依赖边界

第三方插件只能依赖 `PUBLIC_CORE_MODULES` 中的公共模块。永远禁止：

```python
from core.trunk import Trunk
from core.data_schema import WATCHED
from core.data_migrations import migrate_all
from core.secret_store import SecretStore
from core import *
```

官方随包模块可以依赖少量审计过的集成层（例如 `core.auto_update_*`、
`core.computer_*`），但 `core.trunk`、`core.data_schema`、
`core.secret_store` 等仍然禁止。

### 3.3 强制执行点

| 入口 | 检查 |
|---|---|
| 插件市场安装仓库模块 | 验签 -> 清单 api_version -> AST 依赖边界 -> 语法/加载 |
| 插件市场下载在线模块 | 验签 -> 清单 api_version -> AST 依赖边界 -> 原子落盘 |
| 本地 `.py` 安装 | 按第三方插件严格检查 core 依赖 |
| `tools/check_plugin_api.py` | 检查已安装模块与 manifest |
| CI 兼容矩阵 | 每个 Python 版本都跑插件 API 检查 |

### 3.4 发布流程

```powershell
set X6_KEY_VAULT=E:\xiao6-keys
py -3 tools/rebuild_modules_repo.py --apply
py -3 tools/sign_modules.py
py -3 tools/check_repo_sync.py
py -3 tools/check_plugin_api.py
```

改 `modules/installed/` 后漏掉 rebuild 或 sign，用户端会因哈希/签名不一致
拒绝安装；依赖 core 私有实现的第三方插件会在安装前被静态检查拦住。
