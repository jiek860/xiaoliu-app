一、整体架构
────────────────────────────────────────
微核星型架构：核心是 core/trunk.py 总线，所有模块通过 trunk.call() 调用，
模块之间不直接互相 import（这条约束让任意模块都能单独装卸而不牵连别人）。
※ 例外：模块间允许"直接 import 同一进程内的纯工具类"，实测只有 1 处
  （plugin_market 直接 from core.plugin_signer import PluginSigner）。

二、能力架构（v25.2.0 核心变化）
────────────────────────────────────────
【要解决的问题】
  以前"一个能力"要能让模型调用，得手工改三处代码：tool_caller 里的工具表、
  提示词、分发分支。结果是：能调用的能力长期只有 19 个，而项目里登记着 72 个
  模块 —— 大量功能只能靠点按钮，模型够不着，坏了也没人发现
  （memory_organizer.check_conflicts 就因为"只能手点"，文件对象切片那个
   TypeError 藏了很久，那功能其实从来没成功过）。

【现在怎么做的】
  能力**声明式**注册，两个来源：

  来源A  插件模块（modules/installed 里那 43 个）
         在类里声明 TOOLS，例如：
             TOOLS = [
                 {"name": "weather_now", "method": "get",
                  "desc": "查某个城市现在的天气",
                  "args": {"city": "城市名，如：杭州"},
                  "readonly": True,
                  "hints": ["天气", "气温", "下雨"]},
             ]
  来源B  core 模块（core/ 里那 24 个，不是插件、没有清单条目）
         在 core/core_caps.py 里集中声明

  ⚠️ 安全要点：来源A **运行时从模块源码读 TOOLS**（用 AST，不执行模块代码），
     而不是读 modules_repo/manifest.json 里那份。原因：
     RSA 签名覆盖的是**模块文件的 sha256**，清单条目的其它字段（含 tools）
     不在签名覆盖范围内 —— 改清单里的 tools，验签照样通过。
     改源码必然改变文件哈希 -> 验签失败。所以读源码，声明才真正受签名保护。
     清单里那份只是给市场列表/界面看的副本。

【字段含义】
     name      工具名（模型看到的）
     method    模块里的方法名
     desc      给模型看的一句话说明
     args      {参数名: 说明}，模型会按这个填
     readonly  只读 —— 不加确认、不转后台
     confirm   要确认（没确认界面时**拒绝执行**，不会静默跑）
     danger    危险操作（还要规则允许）
     bg        长任务 —— 聊天触发时转后台线程，不卡回复
     hints     关键词，用于两级筛选

【两级筛选：为什么不让模型看全部 63 个工具】
  实测 _llm_decide 的提示词：63 个工具不筛选要 3761 字符，
  而且**候选里混着不相关的能力会拉低模型选择准确率**（工具越多越容易挑错）。
    第 0 级  core/pipeline/context_builder._TOOL_HINTS  不像要动手就不进 tool_caller
    第 1 级  tool_caller._candidates()  按模式收窄 + 按 hints 缩到 ~15 个
  实测效果：粗筛后最坏 889 字符（阈值 1155）
  hints 匹配用 2 字滑窗，解决"整理记忆" vs "帮我整理下记忆"这类说法差异。

【工具模式预设】core/tool_presets.py
    全部   可用 57 / 57   ← 默认，不过滤（行为与加这机制之前完全一致）
    日常   可用 22 / 57 （查资料、记事、看统计，不碰文件系统和命令）
    干活   可用 15 / 57 （操作电脑、看界面、跑命令、动文件）
    编程   可用 10 / 57 （只留工程向，提示词 889 -> 574 字符）
    维护   可用 12 / 57 （记忆整理、数据清理、导出、体检）
  规则「工具.模式」控制，落盘 data/rules/rules.json。
  模式只收窄**给模型看的候选**，不影响命令面板里能搜到什么。
  三重防御：模式名不认识→不过滤；为 None→不过滤；过滤后为空→原样返回。

【长任务后台执行】
  聊天触发的工具调用是被回复流程**同步**调用的
  （core/pipeline/legacy_reply.py:133、context_builder.py:200），
  所以自动更新闭环这类要跑几分钟的能力会把整条回复卡死。
  标了 bg: True 的会转后台线程（threading，不依赖 Qt），
  立刻返回「已在后台开始」，完成后写日志 + 状态栏提示。
  当前 7 个：auto_update / task_goal / learn_topic / debate / model_vote
            / migrate_export / crash_export

七、线程安全约定（重要）
────────────────────────────────────────
Qt 规定**控件只能在 GUI 线程碰**。子线程直接改控件会随机崩，
这类 bug 在本项目已出现两次：
    · gui/model_manager_dialog.py   在 threading.Thread 里 list_w.clear()
    · gui/mixins/voice_mixin.py     在子线程里 self.input.setPlainText(...)
                                    （注释还写着"回到主线程更新UI"，其实没回）

【正确做法】子线程只 emit 信号，槽函数在 GUI 线程执行：
    class _VoiceRelay(QObject):
        done = pyqtSignal(str, str)
    relay.done.connect(self._on_voice_done)   # 槽在 GUI 线程跑
    def _do_listen():                          # 子线程只做识别
        ...
        relay.done.emit(text, err)             # 跨线程 emit 是安全的
  中继对象要以窗口为父 + 引用挂到 self 上，否则会被回收、信号没人接。

【为什么 status_cb 安全】
    self.trunk.status_cb = self.statusMessage.emit   # 暴露的是 emit，不是控件函数
  所以后台线程调 trunk._set_status() 是安全的。

【自动检查】tools/check_threads.py 会扫全部线程入口（当前 39 个），
  用 AST 精确取函数体（end_lineno，不靠正则猜），发现子线程碰控件就报错。

十一、按钮精简（v25.2.0）
────────────────────────────────────────
【背景】实测 GUI 里有 114 处控件创建、27 个文件。其中"实用工具"面板一个人
就占 24 个按钮 —— 而那 24 条能力里 23 条其实"说一句"就能用。
按钮多不是功能多，是**功能的统一调用入口缺失**，只能一个功能配一个按钮。

【做了什么】114 -> 108
  1. "实用工具"面板 24 个按钮 -> 命令面板（Ctrl+K）
     数据来自能力注册表，模块声明 TOOLS 就自动出现，不用手写按钮表
  2. 系统面板 4 个"点一下就调一个能力"的按钮：
     自动更新闭环 -> auto_update    开始学习 -> learn_topic
     任务闭环     -> task_goal      采纳建议 -> learn_topic（见下）
  3. 日志中心 2 个**重复入口**：
     导出日志包 -> 注册表里已有 crash_export
     导出数据   -> 注册表里已有 migrate_export
     （这两个按钮走的是另一套局部实现，同一件事两个真相，已一并清掉）

【⚠️ 撤按钮的顺序：先声明能力，再撤按钮】
  撤按钮 != 删功能。每个撤掉的按钮，能力都先在注册表里声明好、验证可调用，
  才动按钮。撤完逐个核对："能力在注册表里吗 / 签名能调吗 / 命令面板搜得到吗"。

【顺带修掉的 bug】「✅ 采纳建议（学第一条）」从来没工作过：
  它读的是建议文本框的第一行，而那个框全项目只有一处
  setPlainText("🤔 正在生成建议...")，之后再没人填过内容 ——
  等于每次拿这句占位符去网上搜。撤掉它、改成声明 learn_topic 才是正解。

【不再撤的原因】剩下 108 个里绝大多数是**交互本身**，不是功能入口：

【方向 2：逐个判断"自己吞异常"的能力方法】
  审计出 10 条能力的**方法体自己**吞异常。这类最危险：异常到不了分发层，
  调用方拿到"半成品结果"，看起来像成功。

  🔴 最重的一条是**真·数据丢失** —— memory_organizer.auto_organize：
       读记忆卡时 `except: pass` 跳过解析失败的行，
       写回却是 `open(path, "w")` **全量覆盖** -> 那几行被**永久删除**。
       更隐蔽的是返回值：`"原始": len(cards)` 报的是**解析成功的条数**，
       不是文件行数。于是 {"原始": 5, "保留": 5} 看起来"一条没丢"，
       文件里却可能有 8 行 —— **数据丢了，报告还说没事。**
       修法：坏行**原样保留**（解析不了不代表该删）、报出坏行数与明细、
       "原始"改为文件真实行数、写回改成临时文件 + os.replace。

  🔴 第二条**比"静默"更糟** —— startup_optimizer.precompile：
       `py_compile.compile(f, doraise=False)` **根本不抛异常**
       （它把 SyntaxError 打到 stderr 就返回 None），
       于是 `except` 永不触发，`count += 1` 反而**把编不过的文件也算成成功**。
       实测：一个正常文件 + 一个语法错文件 -> 返回 {'预编译文件': 2}。
       改成 doraise=True 才真的能捕获并报告。

目标：解决设置、工具、插件、MCP、安全中心、任务中心、记忆、知识库都在增加，普通用户不知道现在该去哪里的问题。

### 一、问题定义

#### 1.1 当前表现

- 首屏同时出现：新建对话、历史、模块按钮、设置、登录、清空、附件、语音输入、实时对话、模型、代码编辑器、发送。
- 设置窗口有 6 个标签页：模型 / 界面 / 工具 / 扩展 / 记录 / 系统。
- 高级能力分散在设置、命令面板、模块按钮、任务中心、安全中心、知识库、记忆、插件、MCP。
- 普通用户第一次打开时，无法回答三个问题：
  1. 我现在应该先做什么？
  2. 复杂任务应该点哪里？
  3. 出了问题、权限被拒绝、任务失败，下一步去哪？

#### 1.2 根因

不是功能不够，而是：

- **入口层级过深**：高频动作和低频配置混在一起。
- **没有主路径**：聊天、任务、知识库、插件都是并列入口。
- **模式缺失**：高级功能和普通对话没有视觉区分。
- **缺少下一步引导**：空状态、失败状态、权限状态没有行动指引。

#### 1.3 设计目标

1. 普通用户默认进入**简单模式**，首屏只保留 7 个以内主要按钮。
2. 复杂请求有**统一任务入口**，不再让用户猜这是聊天还是任务。
3. 高级功能不删除，只**折叠到高级模式/更多菜单**。
4. 每个关键状态都给**唯一下一步**，而不是只报错。
5. 所有入口统一由 `FeatureRegistry` 管理，避免以后继续散落。

### 五、统一任务入口

#### 5.1 输入框模式切换

输入框左下角增加分段控件：

```text
[ 聊天 ] [ 任务 ]
```

- **聊天**：普通问答，不强制拆步。
- **任务**：进入任务运行时，显示计划、步骤、确认、结果。
- 复杂输入自动切换到任务模式，并提示这看起来是一个任务，已切换。

#### 5.2 复杂请求自动识别

在 `Trunk._should_auto_task()` 基础上增加：

- 长度 > 16；
- 包含强动作词：整理、分析、批量、生成报告、检查并修复、制定计划、完整流程；
- 包含多个动作/多个对象；
- 用户明确点击任务。

自动切换规则：

```text
普通问答 -> 聊天
单步工具 -> 聊天，但显示工具步骤
多步/长任务 -> 任务模式
高风险操作 -> 任务模式 + 确认
```

#### 5.3 任务入口统一

所有任务入口最终都打开同一个任务页面：

- 侧栏任务；
- 输入框任务模式；
- 聊天回复里的转为任务；
- 命令面板任务中心；
- 后台 scheduler 定时任务（无独立按钮，统一汇入任务中心）；
- 子智能体任务。

统一任务页包含：

- 目标；
- 计划；
- 当前步骤；
- 等待确认；
- 结果；
- 重试/取消/继续；
- 引用/产物。

## UI 缺陷修复：按钮文字被压扁（2026-10-22）

### 现象

工作台工具条上的按钮（▶开始 / ⏸暂停 / 🛑取消 / ⛶弹出 / 📄新建…）
只显示出一条横线，看不到中文。

### 根因

`gui/style.py` 的全局 `QPushButton` 样式：

```css
QPushButton {
    padding: 10px;          /* 上下各 10px */
    padding-left: 15px;     /* 只覆盖左边 */
    font-size: 13px;
}
```

而工具条按钮通过 `setFixedHeight()` 固定在 24~27px：

```text
24px(高度) - 20px(上下padding) - 2px(边框) = 2px 可用
13px 的中文只剩 2px → 被裁成一条横线
```

### 修复

```css
QPushButton {
    padding: 4px 12px;      /* 上下 4px，左右 12px */
    min-height: 24px;       /* 保证一行中文放得下 */
}
QCheckBox {
    min-height: 22px;       /* 复选框同样的问题 */
    padding: 2px 4px;
}
```

同时把工作台里固定高度的按钮从 24/26 提到 28/30，留出不同 DPI 下的余量。

### 为什么不是简单加大按钮高度

按钮高度由布局统一控制（工具条、网格），全局加高会让所有界面变松散。
调整 padding 是"最小侵入 + 全局生效"的做法：
凡是使用全局样式的按钮都自动修好。

### 回归测试

```python
def test_global_button_padding_leaves_room_for_text():
    assert "padding: 10px" not in STYLE
    assert b.height() >= fm.height() + 8
```

## 代码 Agent 能力层（2026-10-24）

代码 Agent 从"一次性 patch"升级为**可配置轮次、可预演回滚、可断点续跑、可推送 PR** 的闭环。

### 新增核心模块

| 文件 | 职责 |
|---|---|
| `core/code_agent_policy.py` | 轮次上限（默认 12，范围 1~15）+ 显式终止条件 |
| `core/symbol_parser.py` | 真符号索引：Python AST；JS/TS 优先 tree-sitter，未安装时正则降级并标 `engine/confidence` |

| `core/code_roles.py` | 双角色 Agent：探索 Agent（只读工具 + report）→ 修改 Agent（带 report 出 patch） |
| `core/github_pr.py` | 只用 `api.github.com`：blob→tree→commit→ref→PR→check-runs→merge |
| `gui/inline_diff.py` | 编辑器内联 diff 预览：点击行跳转 + 应用/撤销（QLabel 链接，不占按钮预算） |

### 执行链路

```text
工作台 AI 面板
  └─ CodeTaskQueue.enqueue(goal)            data/code_jobs/queue.json
      └─ AgentOrchestrator（max_code_rounds）
```

> 注意：本清单曾长期保留"自动测试、lint、失败回修、多文件 patch、diff 审批、回滚未完成"的旧结论，
> 与代码实际状态不符。以上述核对结果为准，后续规划不要重复立项。


## 0. 结论先行

小6当前不是功能不足，而是能力已经存在，但还没有形成成熟产品应有的闭环。

三个最关键的差距：

1. **使用感受**：任务过程不够透明，失败恢复不够统一，长任务和后台活动不可见，对话缺少编辑、重试和分支。
2. **代码能力**：编辑器目前是可用编辑器，AI 改代码还是生成完整文件并替换，没有形成项目理解 -> 多文件 patch -> diff 审批 -> 测试回修 -> 回滚的闭环。
3. **电脑操控**：动作能力齐全，但缺少感知 -> 规划 -> 执行 -> 验证 -> 重试/回滚的视觉 Agent 闭环。

本方案的目标不是简单增加按钮，而是把现有能力统一到一套可观测、可恢复、可审计的 Agent Harness 中。

目标形态：

```text
用户目标
  -> 计划
  -> 工具/模型执行
  -> 结果验证
  -> 失败诊断
  -> 自动重试或请求用户
  -> 结果交付
  -> 可回放、可撤销、可继续
```

## 1. 设计原则

### 1.1 一个 Agent Harness，多个执行域

聊天、任务、代码、电脑操控不要各自维护一套状态机。以现有 `core/task_runtime.py` 为基础，扩展为统一执行 harness，代码修改和电脑操作都作为 harness 的一类执行域。

### 1.2 每一步必须有状态、原因和验证条件

每个步骤至少记录：

- 做什么
- 为什么做
- 用了哪个工具或模型
- 开始/结束时间
- 消耗的 token、费用和时间
- 结果摘要
- 验证条件
- 失败原因
- 可执行的下一步
- 是否可回滚

### 1.3 失败不是终点，而是一个结构化状态

统一错误信封：

```json
{
  "ok": false,
  "code": "NETWORK_DENIED",
  "title": "网络被拒绝",
  "message": "这次请求被安全策略拦截",
  "cause": "目标域名不在允许列表中",
  "next_action": {
    "id": "open_security_network_events",
    "label": "查看安全中心网络事件"
  },
  "technical_detail": "...",
  "task_id": "task_..."
}
```

UI 只展示 title、message、next_action；技术细节折叠。

### 1.4 UI 不等待，状态主动推送

所有长任务、模型调用、工具调用、文件修改、测试执行都在后台运行。主线程只负责渲染状态和接收事件。

### 1.5 安全边界内自动化

- 低风险动作自动执行并记录。
- 中风险动作展示预览并确认。
- 高风险动作必须二次确认，默认 fail-closed。
- 所有动作有审计记录，代码修改有备份，电脑操作有回滚依据。

### 1.6 向 DeepSeek Harness 类 Agent 框架靠拢

本方案中向 DeepSeek Harness 靠拢定义为以下工程原则，不依赖某个特定产品的内部实现：

- 工具 schema 化，而不是自由文本解析
- Observation -> Plan -> Act -> Verify -> Reflect 循环
- 明确的执行状态机和 checkpoint
- 上下文压缩与长期记忆分层
- 工具调用、权限、沙箱、审计统一入口
- 任务可回放、可恢复、可中断
- 每个动作都有验证和失败恢复策略
- 计划器、执行器、验证器职责分离
- 预算、超时、重试和幂等控制

### 4.2 项目索引

- 文件树

```text

  meta.json
```

更新策略：

- 启动时增量扫描
- 文件保存后局部更新
- 大批量修改后后台重建
- 索引损坏时自动重建

### 4.3 多文件 Patch Engine

新增 `core/patch_engine.py`。

Patch 格式：

```json
{
  "patch_id": "p_...",
  "goal": "修复设置窗口保存失败",
  "files": [
    {
      "path": "gui/settings_dialog.py",
      "base_hash": "sha256...",
      "hunks": [
        {
          "old_start": 120,
          "old_lines": ["..."],
          "new_lines": ["..."],
          "reason": "修复 None 引用"
        }
      ]
    }
  ],
  "risk": "medium",
  "tests": ["pytest tests/test_settings_entries.py -q"]
}
```

安全要求：

- 应用前检查 base_hash
- 每个 hunk 必须能唯一匹配
- 冲突时拒绝应用，不覆盖用户修改
- 自动备份原文件
- 支持文件级和 hunk 级接受/拒绝
- 支持一键撤销本次 patch

### 4.4 Diff 审批窗口

新增 `gui/diff_dialog.py`。

功能：

- 文件列表和变更统计
- 文件级接受 / 拒绝
- hunk 级接受 / 拒绝
- 风险等级
- 修改原因
- 影响文件
- 测试计划
- 应用后自动执行验证

### 4.5 测试与自动回修

流程：

1. 应用 patch
2. 运行配置好的测试/lint/编译命令
3. 解析失败输出
4. 将失败文件、traceback、测试用例反馈给模型
5. 生成下一轮 patch
6. 最多重试 N 次
7. 失败后将工作区恢复到 patch 前状态，并给出下一步

测试命令来源：

- 项目配置
- `pyproject.toml`
- `pytest.ini`
- 用户设置
- 自动探测

### 4.6 代码工作区运行环境

在现有 `gui/code_editor_dialog.py` 基础上增加：

- 项目虚拟环境选择
- 工作目录
- 环境变量
- 内置终端
- 当前文件运行
- 项目任务运行
- 端口/服务检测
- 长进程管理
- 运行历史

短期不追求完整 IDE，但需要具备代码 Agent 可执行验证的最小运行环境。

### 4.7 Git 与回滚

- 显示当前分支和 dirty 状态
- patch 应用前检查工作区是否干净
- 支持生成临时分支或 stash
- 支持撤销本次 Agent 修改
- 支持查看 patch 对应的 commit/diff
- 冲突时停止，不自动覆盖

### 4.8 验收指标

- 能定位并修改至少 2 个相关文件
- 所有修改先展示 diff
- 支持按文件/按 hunk 接受
- 应用后自动跑测试
- 测试失败能自动产生第二轮 patch
- 任何一次 Agent 修改都能一键回滚
- 修改过程有完整 trace 和测试报告

## 5. 电脑操控 Agent 方案：向 DeepSeek Harness 类执行框架靠拢

### 5.1 核心循环

```text
Observe
  -> 截图
  -> 可访问性树 UIA
  -> OCR / 视觉理解
  -> 当前窗口和屏幕状态

Plan
  -> 目标拆解
  -> 选择应用/窗口
  -> 选择控件或坐标
  -> 预估风险和验证方式

Act
  -> 点击 / 输入 / 快捷键 / 滚动 / 文件操作
  -> 每次只做一个可验证动作

Verify
  -> 再截图
  -> 检查窗口标题、控件状态、文本变化、文件变化
  -> 判断成功 / 失败 / 需要重试

Reflect
  -> 更新世界状态
  -> 失败时分析原因
  -> 重试、回退或请求用户
```

### 5.2 感知层

新增统一感知结果：

```json
{
  "screen": {
    "size": [1920, 1080],
    "scale": 1.25,
    "active_window": "记事本",
    "monitor": 0
  },
  "accessibility": {
    "windows": [],
    "controls": [
      {
        "id": "uia_17",
        "name": "保存",
        "type": "ButtonControl",
        "rect": [100, 200, 80, 30],
        "enabled": true
      }
    ]
  },
  "vision": {
    "text_blocks": [],
    "detected_buttons": [],
    "description": "当前窗口是..."
  }
}
```

感知优先级：

1. UIA 控件树
2. 浏览器 DOM/可访问性信息（后续）
3. OCR / 视觉模型
4. 原始坐标兜底

### 5.3 动作 schema

所有电脑动作用类型化 schema 表达：

```json
{
  "action_id": "act_...",
  "type": "click|type|hotkey|scroll|open_app|activate_window|read_file|write_file|shell",
  "target": {
    "kind": "uia|vision|coordinate|window|path",
    "id": "uia_17",
    "text": "保存",
    "rect": [100, 200, 80, 30]
  },
  "args": {},
  "risk": "low|medium|high",
  "verify": {
    "type": "window_title|control_visible|text_changed|file_exists|exit_code|screenshot_diff",
    "expected": "..."
  },
  "rollback": {
    "type": "none|restore_file|hotkey|screenshot_restore"
  }
}
```

### 5.4 计划器 / 执行器 / 验证器分离

- **Planner**：只产出计划，不直接操作电脑。
- **Executor**：只执行经过 schema 校验的动作。
- **Verifier**：只检查执行结果，不修改状态。
- **Recovery Manager**：失败后选择重试、回退或请求用户。

这样可以避免模型边想边乱点。

### 5.5 视觉 grounding

目标元素定位采用多源融合：

- UIA name/type 精确匹配
- 控件文本模糊匹配
- OCR 文本 + 位置匹配
- 截图视觉模型候选
- 坐标置信度打分

输出：

```json
{
  "candidate_id": "uia_17",
  "confidence": 0.92,
  "source": "uia+ocr",
  "risk": "low"
}
```

置信度低于阈值时：

- 请求用户确认
- 或先放大/滚动/聚焦窗口重新感知

### 5.6 动作后验证

每个动作都带验证条件：

| 动作 | 验证 |
|---|---|
| 点击按钮 | 目标窗口标题/控件状态变化 |
| 输入文本 | 目标输入框内容包含输入内容 |
| 打开应用 | 窗口出现 |
| 保存文件 | 文件 mtime/size 变化 |
| 命令执行 | exit code + 输出 |
| 页面导航 | URL/标题/可见文本变化 |
| 截图操作 | 截图哈希/区域差异 |

验证失败后：

1. 重新截图
2. 重新定位目标
3. 重试 1-2 次
4. 仍失败则停止并给出下一步

### 5.7 回滚与审计

- 文件修改前备份
- 高风险操作前保存快照
- 每个动作记录前后截图
- 记录动作 schema、参数、耗时、结果
- 支持按任务查看操作回放
- 支持撤销文件操作
- 系统级操作不可逆时，在执行前明确说明

### 5.8 跨应用工作流

用一个统一的任务模型表示跨应用步骤：

```json
{
  "goal": "把浏览器查到的内容整理到 Excel",
  "steps": [
    {"app": "chrome", "action": "search", "verify": "结果页出现"},
    {"app": "chrome", "action": "extract_text", "verify": "文本非空"},
    {"app": "excel", "action": "write_rows", "verify": "文件已保存"},
    {"app": "excel", "action": "screenshot", "verify": "表格可见"}
  ]
}
```

要求：

- 每一步有验证条件
- 应用切换有窗口激活确认
- 失败时可回退到上一步
- 支持录制、参数化和重放

### 5.9 命令执行权限

保留现有安全边界，但提供可操作的权限流程：

- 按任务授予临时命令权限
- 展示完整命令、工作目录和影响
- 在沙箱内执行
- 超时、输出上限、环境变量清理
- 危险命令单独确认
- 完整审计和回放

### 5.10 跨平台适配层

新增抽象接口：

```python
class ComputerAdapter:
    def observe(self): ...
    def find(self, target): ...
    def act(self, action): ...
    def verify(self, condition): ...
    def screenshot(self): ...
```

首个实现：Windows UIA + Win32。后续可增加 macOS Accessibility、Linux AT-SPI。

# Agent 可控闭环落地方案与实施记录

版本：v1.0  
日期：2026-10-19  
状态：已实施并通过全量测试

## 1. 目标

把已有能力串成一条稳定、透明、可中断、可恢复的用户旅程：

```text
用户输入目标
  -> 自动路由（代码 / 电脑 / 对话）
  -> 计划或单步决策
  -> 执行
  -> 验证
  -> 失败重新观察 / 重新规划
  -> 过程可见、可暂停、可取消、可人工接管
  -> 完成后有结果、产物、diff/截图、测试报告
  -> 一键撤销
```

核心原则：

1. **一个入口**：普通用户只面对一个目标输入框；
2. **每一步有状态**：计划、观察、动作、验证、失败原因、下一步；
3. **每个动作可控制**：暂停、继续、取消、人工接管；
4. **每个改动可恢复**：代码 patch 和电脑文件操作都有回滚清单；
5. **权限统一**：代码 Agent、电脑 Agent 都经过 Agent 权限入口和审计；
6. **视觉结果可执行**：UIA/OCR/多模态候选统一带 element_id、rect、confidence；
7. **失败不是终点**：动态循环会重新观察并重新规划，而不是只重试旧动作。

## 3. 原始问题逐项闭环

### 3.1 代码 Agent 默认测试命令 NameError

- 修复：`core/code_agent.py` 显式 `import sys`；
- 增强：自动探测 pytest / npm / cargo / go 测试命令；
- 无测试命令时返回 `skipped=True` 和明确原因，不再假装测试通过；
- 命令统一走可暂停、可取消、可超时的 `Popen` 执行器。

### 3.2 control_visible 误判

- 修复：只有 `ui_find()` 返回 `ok=True` 且找到控件数量大于 0 才算可见；
- 回归测试：`test_control_visible_failed_dict_is_not_success`。

### 3.3 视觉 grounding 未接入执行

- UIA / OCR 候系统一输出 `element_id + rect + confidence + source`；
- 规划器提示词直接携带候选 element_id、rect、confidence；
- 执行器优先按 element_id 查找，其次 UIA 名称，再次 rect 中心坐标；
- OCR 行若带 `@(x,y,w,h)` 会保留坐标；
- 截图后自动框选目标区域，供用户核对。

### 3.4 计算机 Agent 不是动态循环

- 新增 `run_goal_dynamic()`：
  - 每一步重新观察；
  - 单步规划；
  - 执行；
  - 验证；
  - 失败反馈给规划器；
  - 下一轮可以换定位方式或换动作；
- `plan_next()` 增加 done 判断、历史、反馈和最新屏幕候选；
- 旧 `run_goal()` 保留兼容，GUI 新路径使用动态循环。

### 3.5 Patch 不能新建/删除/重命名

- `patch_engine` 增加 `op`：
  - `update`：hunk 修改；
  - `create`：创建新文件；
  - `write`：整文件写入；
  - `delete`：删除；
  - `rename`：重命名；
- 支持顺序操作模拟：create/rename 之后可以继续 update；
- 回滚清单记录 existed / backup / new_path，可逆恢复；
- 空白差异做受限模糊匹配，仍拒绝歧义匹配。

### 3.6 暂停/取消/接管

- `CodeAgent` 与 `ComputerAgent` 都有：
  - `cancel()`；
  - `pause()`；
  - `resume()`；
  - 可中断等待和可杀死子进程；
- 代码 Agent 命令执行使用 `Popen`，取消/超时会终止进程树；
- 电脑 Agent 每一步之间检查取消/暂停；
- GUI 提供暂停、继续、取消、人工接管按钮；
- 关闭窗口时提示会取消任务，并等待线程退出。

### 3.7 一键回滚没有入口

- 代码 Agent 弹窗新增「一键撤销」，调用 `rollback_all()`；
- 电脑 Agent 弹窗新增「一键撤销」，调用 `rollback_run()`；
- 统一 Agent 旅程窗口也有「一键撤销」；
- 电脑文件操作记录备份：write/edit/delete/copy/move；
- 支持动作自带 `rollback` 的 hotkey/press_key 回退。

### 3.8 入口割裂

- 新增统一 Agent 旅程窗口，一个输入框自动路由；
- 普通聊天输入明确代码/电脑任务时，会提示进入 Agent 旅程；
- 命令面板和更多菜单增加「Agent 旅程」入口；

### 3.9 过程不透明

  - 步骤列表；

### 3.14 代码 Agent 项目理解浅

- 上下文从最近文件 + 首段文本升级为：
  - 关键词命中；
  - AST 符号；
  - import / 测试关联；
  - 当前打开文件；
  - 最近修改文件；
  - 命中行附近代码片段；
  - 用户选中文本；
  - 文件符号大纲；
- 总上下文预算仍是可控的，避免一次性塞爆模型。

> 2026-10-24 更新：符号部分已换成真索引 —— Python 用 AST，JS/TS 优先
> tree-sitter（未安装时正则降级并标 `engine/confidence`），见
> `core/symbol_parser.py` 与 `docs/20_优化路线与实施记录.md` 同日条目。

### 3.15 一次性 patch，不是探索 Agent

- 模型可返回探索工具调用：
  - read_file；
  - grep；
  - list_files；
  - find_symbols；
  - run_command；
- 工具结果回填给模型，再进行下一轮；
- 达到最大探索轮数后明确失败，不无限循环。

> 2026-10-24 更新：已升级为双角色（探索 Agent 只读产报告 → 修改 Agent 出 patch），
> 轮次上限默认 12、夹取 1~15 且支持断点续跑；多文件 patch 应用前先整体 dry-run。
> 见 `core/code_roles.py`、`core/code_agent_policy.py`、`core/code_task_queue.py`。

### 3.16 测试/lint/工程环境

- 自动探测 pytest / npm / cargo / go；
- lint 探测 ruff / npm lint / cargo clippy / gofmt；
- 测试和 lint 均走统一命令执行器；
- 支持超时、取消、输出上限、退出码。

> 2026-10-25 更新：失败轮不再直接结束任务 —— patch 生成/校验失败、
> dry-run 不匹配、空 patch 都会带回错误进入下一轮；回修提示同时注入
> 上一轮已应用的 diff。测试/lint 失败反馈改为先列失败用例名
> （`文件::用例:L行`）再附输出尾部，模型更容易定位。

## 闭环的 UI 承载（2026-10-22）

Agent 闭环（计划 → 执行 → 审批 → 回滚）现在有统一的可视化承载：

```text
gui/workbench_dialog.AgentDock
  ├─ goal        目标输入
  ├─ start/pause/cancel   执行控制
  ├─ timeline    实时步骤（事件流）
  └─ _approve()  diff / 电脑动作审批（DiffReviewDialog）
```

底层仍是 `core/agent_orchestrator.AgentOrchestrator`：

```text
route(goal) → code / computer / chat
  code     → CodeAgent（patch 审批）
  computer → ComputerAgent（动作审批）
```

### 关键约束

| 约束 | 原因 |
|---|---|
| 审批回调 fail-closed | diff 打不开时必须拒绝，不能默认放行 |
| 不阻塞 UI 线程 | 事件通过 `event_cb` 回主线程追加到 timeline |
| 暂停 / 取消 可随时触发 | 长任务必须能立刻停手 |

## 四、完整度口径 v2（2026-10-25 起）

旧口径只有三项：有 docstring、有同名测试、≥80 行。它会把
`panel_registry`、`safe_http`、`diagnostics` 这类**薄适配层**误判成
"骨架"——它们本身就只有几十行，但被全项目大量调用，删了会全线报错。
v2 增加两项判定：

1. **入口可达**：能从一个真实入口走到，包括 GUI 按钮/菜单、
   `trunk.call(...)`、`FeatureRegistry` 注册、`core/lazy_config.py` 懒加载表。
2. **跨模块测试覆盖**：除了同名测试，还有别的测试文件在验证它
   （例如 `test_plugin_api.py` 覆盖 `plugin_broker`，
   `test_download_verification.py` 覆盖 `auto_updater` 的下载链路）。

等级定义：

| 等级 | 判定 |
|---|---|
| 完整 | docstring + 同名或跨模块测试 + ≥80 行 + 入口可达 |
| 基本完整 | docstring + ≥80 行，且入口可达与测试至少满足一项 |
| 部分 | 有真实业务逻辑，但缺入口或测试之一 |
| 骨架 | <80 行且无真实入口、无调用方（薄适配层除外，见下） |
| 薄适配层（非骨架） | <80 行，但被 ≥3 处调用；单独标注，不计入骨架 |

已知薄适配层（不是骨架，改动前先查调用点）：
`panel_registry`(48 行/1 处)、`plugin_installer`(59/3)、`safe_http`(42/14)、
`diagnostics`(39/201)、`screen_geometry`(42/4)、`onboarding_utils`(55/6)、

## 2026-10-20 启动提速（秒开界面 + 看门狗同时启动）

### 问题

实测（offscreen，本机 Windows 11 / Python 3.12）：

    QApplication 就绪        118 ms
    骨架未拆分时窗口显示    2501 ms
    其中 Trunk.__init__     约 1850 ms
      ├─ 核心模块注册        约 530~700 ms（其中 llm_client 导入 306 ms）
      ├─ vector_store 初始化  约 120 ms
      └─ 模块星图 AST 遍历    约 300~1100 ms

### 改法

1. 新增 `core/startup.py`：纯 stdlib 的启动打点（mark / report / log_summary），
   每个阶段写入 `data/logs/trunk.log` 的一行 `[启动耗时] …`。
2. `run.py` 打点顺序：进程启动 → 依赖路径 → MSVC 预载 → **看门狗拉起** → GUI 导入。
   看门狗（`core/crash_watchdog.spawn`）在主线程还没进 Qt 之前就已经是独立进程，
   所以界面再慢，它也已经跑起来了。
3. `gui/main_window.py` 支持 `boot_signal=False`：只建窗口骨架（标题/图标/样式/占位页）
   立刻显示，`trunk` 置 None 等后台补。
4. 新增 `gui/boot_controller.py`：`QTimer` 把 Trunk 创建排到事件循环之后，
   完成/失败都通过信号回到 GUI 线程；失败自动重试一次，仍失败弹窗说明。
5. `core/trunk_registry.py`：模块星图导出改后台线程（纯展示用途）。
6. `core/llm_client.py`：新增 `defer_warmup=True` 与幂等的 `start_background_workers()`；
   Trunk 启动完成后延迟 1 秒再补启 LLM 看门狗和模型预热，避免和首帧抢 CPU。
7. 可用 `X6_BLOCKING_BOOT=1` 退回"全部就绪才显示"的旧行为（排查用）。

### 结果

| 指标 | 优化前 | 优化后 |
|---|---:|---:|
| 界面可见 | 2501 ms | **155~197 ms** |
| 全功能就绪 | 2510 ms | 约 990~1220 ms |
| 看门狗 | Qt 之后（约 2.5 s） | 进程启动后约 0.3 s，独立进程 |
| 全量测试 | — | 1298 passed / 2 skipped |
| 覆盖率 | — | 约 60.2% |

### 1.2 小6真正的护城河（要守住、要放大）

这些是开源同行**做不到或不屑做**的：

1. **常驻桌面 GUI + 桌面宠物 + 全局快捷键 + 系统托盘**。
   OpenHands 跑在 Docker 里、Cline 活在 IDE 里、Dify 是浏览器里的网站——
   没有一个是"开机自启、住在任务栏、随时被叫起来"的桌面伴生物。
2. **本地优先 + 单机隐私**。数据全在 `data/`、加密、net_guard 拦截私有 IP、
   脱敏审计；Dify 自托管是"服务器上的多租户"，小6是"我电脑上的我自己"。
3. **国内中文体验闭环**：hf-mirror、清华 pip 源、飞书机器人反馈、中文 Windows
   一键安装包、激活码体系、崩溃看门狗独立进程。
4. **电脑控制深度**：UIA+OCR 双通道定位、DPI/多屏/IME、动作后验证、
   有界重试修复——这条链 OpenHands/Cline 都不做（它们管代码仓库，不管你的 Excel 弹窗）。
5. **工程质量**：1300+ 用例、60% 覆盖率、崩溃三层兜底（Python 当场发 /
   看门狗补 / 下次启动补）、RSA 插件签名、SemVer 兼容检查——
   比 90% 的开源 demo 项目工程化程度高一个量级。

## 二、优化方案（按优先级）

> 每条都写清楚：**做什么 / 参考谁 / 为什么小6做了会更强 / 怎么验收**。
> 所有改动都遵循现有规矩：模块之间不互 import、走 trunk.call、子线程不碰 Qt、
> 新功能配测试、按钮走 `feature_registry.py` 预算。

### P0（2 周内，先把最痛的几个洞补上）

#### P0-1. 深度搜索 Agent：把 W1 从"urllib 爬虫"升级为"多跳研究"

**参考**：DeerFlow（字节，30.5K stars）、OpenHands Research。

**做什么**（全部走新模块 `modules/installed/deep_research.py`，不动 deep_search.py）：

1. **接入真搜索 API**：抽象 `SearchProvider` 接口，预置 Brave Search / Tavily /
   Bocha（国内）/ Serper 四个 adapter，用户在设置里填 key 即可。无 key 时降级到现在的
   `deep_search.py` 裸爬。
2. **多跳研究循环**：
   ```
   用户问题
     → LLM 拆 3~5 个子问题
     → 每个子问题并行搜 5 条结果
     → LLM 读摘要 → 决定"要不要补搜下一跳"（最多 3 跳）
     → 汇总 → 带引用链接的中文报告
   ```
3. **引用必须可点**：每条结论后挂 `[1]`，报告末尾列原始 URL；
   失败时明确说"这条没找到来源"，不许编。
4. **后台跑不阻塞**：扔 `task_runtime`，进度在任务中心实时显示"正在搜第 2/4 个子问题"。

**验收**：
- 给一个真实问题（如"2026 年国产开源 Agent 框架对比"），要求 30 秒内出 800 字报告 + ≥5 个真实可访问链接；
- 没配搜索 key 时自动降级到现有 deep_search，不崩；
- 新增 `tests/test_deep_research.py`，mock 搜索 API 测多跳循环和引用格式。

---

#### P0-2. 代码 Agent 升级：git-first 差量编辑 + 测试驱动修复（补 W2 第一阶段）

**参考**：Aider（git-first，每轮最小 diff，自动 commit）。

**做什么**（不改 core/code_agent.py 的现有行为，新增 `modules/installed/coder_pro.py`）：

1. **工作目录隔离**：用户在对话框里选一个本地文件夹作为"项目根"，
   Agent 所有操作限定在这个目录里（`core/path_safety.py` 已有的越界防护直接复用）。
2. **git-first 编辑循环**：
   - 改文件前先 `git status`，如果有未提交改动 → 问用户要不要先 commit/stash；
   - 每次编辑后自动生成 diff 预览，用户点"接受"才落盘；
   - 接受后自动 `git add + commit`（commit message 由 LLM 写，中文）。
3. **测试驱动修复**：
   - 用户说"修一下 xxx 的 bug"时，Agent 先读代码 → 写一个最小复现测试 → 跑测试看红 →
     改代码 → 跑测试看绿 → 汇报。
   - 跑测试用现有的 `core/child_process.py` + `windows_job.py` 超时杀进程树。
4. **Diff 视图**：复用 `gui/diff_dialog.py` 展示 unified diff，红绿配色。

**不做什么**（这一阶段先不上 Docker，避免打包体积爆）：
- 容器级沙箱留到 P1；
- SWE-bench 公开评测留到 P1。

**验收**：
- 给一个有 3 个小 bug 的 Python 仓库，Agent 能在 5 轮内修完并 commit；
- 所有越界路径（`../`）被 `path_safety` 拦下；
- `tests/test_coder_pro.py` 覆盖 diff 生成、commit 流、测试循环。

---

#### P0-3. Trace 可视化回看（补 W6）

**参考**：LangSmith、Arize Phoenix。

**做什么**：

1. 新增 `gui/trace_view_dialog.py`（命令面板 Ctrl+K 可搜"Trace 回看"）。
2. 把 `core/trace.py` 已记录的事件按时间树画出来：
   ```
   2026-10-22 17:55  用户输入
     ├─ 17:55:01  context_builder 检索 3 条记忆 + 2 条向量
     ├─ 17:55:02  tool_caller 选中 browser.open
     │    └─ 17:55:03  browser.open(url=...)  → 200 OK  312ms
     ├─ 17:55:05  llm_client 流式生成 1420 tokens  4.2s
     └─ 17:55:09  post_processor 提取 2 个代码块
   ```
3. 每一点可展开看输入/输出/耗时/错误；支持按模块过滤、按耗时排序。
4. 只读现有 `data/traces/`，不改 trace.py 的写入格式。

**验收**：
- 跑完一次"帮我打开百度搜 xx"后，能在 Trace 窗口里完整看到每一步；

### P1（1 个月内，拉开和桌面同类的差距）

#### P1-1. 可视化工作流编排（补 W3）

**参考**：Dify、Coze Studio、Flowise。

**做什么**（不做拖拽画布那种重资产，先做"轻量 DSL + 简单节点面板"）：

1. 定义一个极简 YAML 工作流格式（存到 `data/workflows/*.yaml`）：
   ```yaml
   name: 每日新闻摘要
   steps:
     - use: deep_research
       with: { query: "今日科技新闻" }
     - use: llm_summarize
       with: { style: "3 条要点" }
     - use: send_feishu
       with: { webhook: "..." }
   schedule: "0 9 * * *"
   ```
2. 新增 `modules/installed/workflow_runner.py`：按 steps 顺序执行，
   上一步输出作为下一步 `{{prev}}` 变量；失败可重试/跳过。
3. 新增 `gui/workflow_dialog.py`：列表 + 运行 + 历史，节点用表单而不是画布
   （PyQt5 做拖拽画布性价比太低，先把"能编排"跑通）。
4. 调度接现有的 `scheduler.py`（modules/installed/scheduler.py）。

**为什么不做拖拽画布**：PyQt5 画布自己写要 2~3 个月，Electron 嵌 Web 又会把打包体积从 150MB 拉到 400MB。先 DSL 后画布。

**验收**：
- 用户能在 5 分钟内搭出"每天早上 9 点搜新闻 → 总结 → 发飞书"；
- 失败重跑、变量传递、日志可见；
- `tests/test_workflow_runner.py` 覆盖变量替换、失败策略、schedule 解析。

   （基于 python:3.12-slim，~150MB）。
2. `core/sandbox.py` 现在是进程级，新增 `DockerSandbox` 后端，
   当用户机器装了 Docker Desktop 时自动启用；没装就回退到进程级。
3. coder_pro 跑测试/装依赖时走 Docker 后端，主机系统零污染。

**为什么放 P1 而不是 P0**：Docker Desktop 在国内个人用户机器上不是默认装的，
强推会把小白用户拦在门外。做成"可选"。

**验收**：
- 沙箱里 `pip install` 不会污染主机；
- 沙箱超时自动 `docker rm -f`，不留僵尸容器；
- 没装 Docker 时优雅回退，不弹错。

---

### P2（季度内，建立长期壁垒）

#### P2-1. 对外 HTTP API + Webhook（补 W8）

**参考**：Dify、OpenHands、LobeChat。

1. 把现有 `bot_server.py` 补成完整 OpenAPI：
   - `POST /v1/chat`（同步）、`POST /v1/tasks`（异步）、`GET /v1/tasks/{id}`；
   - API Key 鉴权，在设置里生成/吊销；
   - CORS 可选开启。
2. Webhook 出站：任务完成/错误时 POST 到用户配置的 URL。
3. 移动端（手机浏览器直接访问局域网 IP）先跑通，原生 App 不做。

#### P2-2. 公开基准回归（补 W9）

1. 在 `tests/eval/` 下接：
   - **SWE-bench lite**：测 coder_pro；
   - **WebArena 简化版**：测 web_agent；
   - 自造一套"中文桌面操作基准"：10 个常见任务（关弹窗、整理文件、查天气、发邮件…）。
2. 每次发版自动跑，分数写进 CHANGELOG 和 ARCHITECTURE.md。
3. 分数低就报警，别再靠"用户说没反应"才知道退化。

#### P2-3. GraphRAG 社区摘要（补 W10）

1. 在现有 `knowledge_graph.py` 上加一层：
   - 实体→社区检测（Louvain）；
   - 每个社区让 LLM 写一段摘要；
   - 检索时先命中社区摘要，再下钻到实体。
2. 这是 RagFlow/微软 GraphRAG 的核心招，小6 已有图基础，加一层就够。

#### P2-4. 异步任务投递模式（补 W11）

1. 用户能"提交一个长任务然后关电脑"——任务在后台跑，
   完成后桌面通知 + 可选推送到手机。
2. 利用现有 task_runtime + auto_update 的通知通道，不重做。

#### P2-5. MCP 市场（补 W12）

1. 内置一份 `data/mcp_catalog.json`：精选 20~30 个社区 MCP server
   （filesystem、git、github、slack、google-maps…），一键填入配置。
2. 复用现有的 mcp_server 信任管理页。

## 三、不做什么（明确边界，避免 scope 膨胀）

| 诱惑 | 为什么不做 |
|---|---|
| 做 Electron 版跨平台 | 现在 Windows 单平台已经 150MB；跨平台要重写 GUI，桌面控制优势在 macOS 上又没了 |

| 把所有开源 Agent 的功能都抄一遍 | 桌面伴生、本地隐私、国内中文、电脑控制——这四个才是小6的赛道，别的都是加分项 |

## 五、验收与不破坏现有规矩

每一条新增功能都要遵守小6现有"不能违反"的规矩：

1. 新模块放 `modules/installed/`，**不互 import**，全部走 `trunk.call`；
2. 子线程不碰 Qt 控件（`tools/check_threads.py` 会拦）；
3. 新工具走 `core/tool_caller` 安全分级（readonly/confirm/danger/bg）；
4. 新 UI 入口在 `core/feature_registry.py` 登记，遵守按钮预算；
5. 改完跑 `check.bat` 七步 + `pytest -q`；
6. 涉及 modules/installed/ 的改动要走"rebuild_modules_repo → sign → check_repo_sync"三步；
7. 版本号单一来源（`core/version.py` + CHANGELOG + 说明.txt）。

## 六、一页纸结论

**小6 不缺"广度"——该有的模型/RAG/插件/MCP/团队/安全都有了；缺的是"深度"和"对外接口"。**

- 广度上已经追平甚至超过 Dify/CrewAI 在单机场景的覆盖；
- 深度上要补：**真搜索、真代码 Agent、真 Trace 回看**；
- 生态上要补：**可自定义角色、可分发的 Skills、可编排的工作流、可调用的 HTTP API**；
- 绝对不能丢：**桌面 GUI、本地隐私、国内中文、电脑控制**——这四个是小6在开源世界里没有对手的位置。

先做 P0 的三件事，两周后就能给用户一个肉眼可见更聪明的小6。

## 三、新的差距（2026 年最新对标发现的）

### D1. Cline 的 Plan/Act 模式
**现状**：我们的 coder_pro 是用户说需求 → Agent 直接开始改。
**Cline 做法**：先出一份完整计划（"我要改这 3 个文件，先加 A 函数，再改 B 逻辑"），用户审批计划后再执行。
**差距**：没有"先出整体计划"这一步，用户只能逐轮审批 diff。
**影响**：复杂任务容易跑偏，用户不知道 Agent 接下来要干什么。

### D2. browser-use 的深度浏览器 Agent
**现状**：web_agent.py 只是"打开网页 → 截图 → VLM 描述"。
**browser-use 做法**：视觉定位元素 → 点击/输入 → 验证结果 → 多步操作循环。
**差距**：我们的浏览器 Agent 是"看一眼"，browser-use 是"会操作"。
**影响**：只能做信息收集，不能做网页上的实际操作（填表、下单、登录）。

### D3. superpowers 的 Skills 生态规模
**现状**：我们有 .x6skill 格式，但只有内置几个。
**superpowers 现状**：11-24 万 stars，说明 Skills 生态是 2026 年大趋势。
**差距**：我们的 Skills 没有市场、没有社区贡献、没有一键安装。
**影响**：用户只能自己写，或者用我们内置的，生态起不来。

### D4. OpenHands 的 SWE-bench 真实成绩
**现状**：我们有 SWE-bench 小样本框架，但没真跑过。
**OpenHands 现状**：60.6% SWE-bench 分数，公开可查。
**差距**：能力没有量化指标，不知道自己在什么水平。
**影响**：改了代码不知道是变好还是变差，全靠感觉。

### D5. Agent 自改进（Hermes Agent 模式）
**现状**：Agent 每次对话都是"白纸"，不会从错误中学习。
**Hermes Agent 做法**：Agent 跑完任务后，自动总结"这次哪里做得不好"，更新自己的提示词/工具偏好。
**差距**：没有自学习机制。
**影响**：同一个错误会犯很多次。

### D6. Cline 的 MCP 市场一键安装
**现状**：我们有 mcp_catalog.json，但要手动复制配置。
**Cline 做法**：MCP 市场浏览 → 一键安装 → 自动配置。
**差距**：catalog 是静态文件，不是交互式市场。
**影响**：用户用 MCP 的门槛还是高。

### D7. 移动端/远程控制
**现状**：有 HTTP API，但没有配套的手机 App。
**对标**：Dify、OpenHands 都有配套的移动端或 Web 控制台。
**差距**：只能坐在电脑前用，不能远程指挥。
**影响**：用户出门了就用不了。

### D8. 多模态深度整合
**现状**：有 multimodal 模块，但和 Agent 的整合是"截图 → 描述 → 继续"。
**对标**：Claude 3.5、GPT-4o 原生支持多模态推理。
**差距**：我们的多模态是"外挂"，不是原生的。
**影响**：复杂视觉任务（看图表、看设计稿）效果差。

## 四、新的优化方向（按优先级）

### P0（最该先补的，1-2 周）

#### P0-1. coder_pro 加 Plan/Act 模式（补 D1）

- **参考**：browser-use

- 记录分数，作为基线
- 以后每次改 coder_pro 都跑一遍对比
- **参考**：OpenHands SWE-bench 报告

### P1（1 个月内）

- 用户能一键启用/禁用
- 支持导入本地 .x6skill 文件
- **参考**：superpowers

#### P1-2. MCP 市场交互版（补 D6）
- 从静态 catalog 升级为交互式列表
- 点"安装"自动写入配置
- 一键测试连通性
- **参考**：Cline MCP Marketplace

#### P1-3. Agent 自学习（补 D5）
- 任务完成后，Agent 自动问"这次做得怎么样？哪里可以改进？"

### P2（季度级）

#### P2-1. 远程 Web 控制台（补 D7）

- 不用做原生 App
- **参考**：Dify Web 控制台

#### P2-2. 多模态原生整合（补 D8）
- 把 multimodal 从"外挂"改成 Agent 的原生能力
- 用户直接发图片，Agent 能看懂并操作
- **参考**：Claude 3.5 Native Multimodal

## 五、小6的护城河（继续守住）

这些是开源同行**做不到或不屑做**的，继续放大：

1. **常驻桌面 GUI + 桌面宠物 + 全局快捷键**——没有一个开源 Agent 是"住在任务栏里"的
2. **本地优先 + 单机隐私**——数据全在本地，加密，不上云

4. **电脑控制深度**——UIA+OCR 双通道，管你的 Excel 弹窗，不管代码仓库
5. **工程质量**——1300+ 测试、崩溃三层兜底、RSA 插件签名

## 六、总结

| 维度 | 评分 | 说明 |
|---|---|---|
| 功能广度 | ⭐⭐⭐⭐ | 12 个短板全部有雏形，比 90% 开源 demo 全 |
| 功能深度 | ⭐⭐⭐ | 每个功能都刚起步，离头部还有距离 |
