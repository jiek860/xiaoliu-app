# 小6 电脑操控能力补全方案

> 目标：让小6 具备 **GUI 操控 + DOM 级浏览器 + 文件/命令** 三类能力，
> 在"操作电脑"这件事上超过豆包（有 DOM 级浏览器）和 DSH（有 GUI 操控）。
>
> 本文是方案，不含已完成的实现细节。实施进度见文末。

---

## 一、三方现状对比（实测过的，不是看文档）

| 维度 | 小6 | 豆包 | DeepSeek Harness |
|---|---|---|---|
| **GUI 桌面操控** | ✅ 34 个方法（pyautogui，真实桌面） | ✅ 虚拟桌面，**不抢你的鼠标键盘** | ⚠️ 有 `BetaComputerToolset`（17 动作）但**未启用** |
| **UI 元素树** | ❌ `uiautomation`/`pywinauto` 未装 | ? | ❌ 无（BetaComputer 也是截图+坐标） |
| **浏览器控制** | ⚠️ `browser.py` 建在 **Playwright**（DOM 选择器级），但**跑不起来** | ❌ 无 DOM/网络级能力 | ⚠️ 有 `BetaBrowserToolset`（40 动作）+ experimental 包，**未启用** |
| **终端/命令** | ❌ `code_runner` 只跑 Python，且黑名单**主动禁掉** `subprocess`/`os.system` | ❌ | ✅ `pwsh`（node-pty，asar 里 83 次命中） |
| **文件读/编辑/搜索** | ⚠️ 只有 create/delete/copy/move + 上传库读 | ❌ | ✅ read/write/edit/glob/grep（ripgrep，97 次命中） |
| **MCP** | ✅ `mcp_client`（328 行） | ❌ | ✅ |
| **工具调用回路** | ✅ `tool_caller`（JSON function calling） | ? | ✅ |
| **子智能体/编排** | ❌ | ✅ 多 Agents 并行 | ✅ subagent + workflow |
| **成熟度** | 自建 | 正式发布 | Beta/experimental（部分） |

**结论：小6 的独特优势是 GUI 操控（DSH 没有）+ DOM 级浏览器（豆包没有）。**
不该照抄 DSH —— DSH 是给开发者的 harness，小6 是桌面助手。

## 二、缺口清单与修法

### 缺口 ①：浏览器跑不起来（**代码已写好，只差两步**）

**实测证据：**
```
playwright 包          ✅ 已装 1.63.0
chromium 二进制        ❌ C:\Users\tt\AppData\Local\ms-playwright 只有 0 MB 锁文件
真跑 open()            ❌ BrowserType.launch: Executable doesn't exist
接线                   ❌ 全项目没有 trunk.call("browser", ...)
                         只有 core/browser_session.py 一个适配器引用它
```

**`browser.py` 已有的能力（11 个动作，DOM 选择器级）：**
`open` / `click` / `type_text` / `get_text` / `fill_form` / `login_and_keep` /
`new_tab` / `scroll` / `screenshot` / `wait` / `get_history`

**修法：**
1. `PLAYWRIGHT_BROWSERS_PATH` 指向 `data/browsers`，跑 `playwright install chromium`
   （放程序文件夹 → 和 `打包给朋友.bat` 一起打包时自带浏览器）
2. `browser.py` 启动前设同一个环境变量（否则运行时找不到）
3. `tool_caller` 工具表加一条 `browser`，让聊天里能用

**风险：** 下载约 150 MB。`data/browsers/` 要进 `.gitignore`（本机产物，不入库）。

---

### 缺口 ②：读不了任意文件

```python
# file_upload.search() —— 只在上传库里找
files = os.listdir(self.upload_dir)
```

**修法：新增 `fs_read` 工具**
- 参数：`path`（可带 `start`/`limit` 做行范围读，长文件不能一次全塞进上下文）
- 复用 `computer_controller` 已有的路径白名单 `_safe_path()`
- 返回：带行号的内容（像 DSH 的 read 那样），便于后续精确编辑

### 缺口 ③：没有精确编辑

**修法：新增 `fs_edit` 工具** —— 老字符串 → 新字符串的精确替换
- 要求 `old_string` 在文件里**唯一**（否则拒绝，防止改错地方）
- 改前自动备份到 `data/backups/`
- 这正是 DSH `edit` 的核心语义，比"整体重写文件"安全得多

### 缺口 ④：没有内容搜索

**修法：新增 `fs_search` 工具**
- 按正则/关键字搜指定目录下的文件内容，返回 `文件:行号: 内容`
- 限定扩展名与目录范围，加结果条数上限
- 纯 Python 实现即可（`os.walk` + `re`），不引入新依赖

### 缺口 ⑤：不能跑命令（**要谨慎设计**）

```python
# code_runner.run_code() 的黑名单 —— 这是刻意的安全取舍，不是漏做
dangerous = ["os.system", "subprocess", "shutil.rmtree", "open(", "eval(", "exec("]
```

**注意两个问题：**
1. 黑名单里的 `open(` 会**误伤正常代码**（`open("a.txt").read()` 直接被杀）
2. 字符串黑名单**本身不可靠**（`getattr(os,"sys"+"tem")` 就能绕）

**修法：新增 `shell` 工具，但不照搬 DSH 的"任意命令"**
- **命令白名单**：`git` / `pip` / `python -m` / `dir` / `type` / `where` / `tasklist` 等
- **全部要确认**：走 `trunk.confirm()`，和删文件同一级别
- **完整日志**：命令 + 输出 + 退出码都记录
- 拒绝：管道、重定向、`&`/`&&`/`;` 串联（先只支持单条命令）
- 默认**关闭**（像 `电脑控制.允许关机` 那样，用规则引擎开关）

> 这一项建议**放到最后做**，并且先只开只读命令（`dir`/`type`/`where`/`tasklist`）。

### 缺口 ⑥（可选）：子智能体 / 编排

DSH 的 `subagent` + `workflow` 能扇出几十个并行任务。小6 现在是"单队列 + 后台线程"。
这一项工程量最大，**不建议现在做** —— 先把能力补齐，再考虑编排。

| 顺序 | 事项 | 成本 | 收益 | 风险 |
|---|---|---|---|---|
| **1** | 修活浏览器（下载 + 接线） | 很小 | **DOM 级浏览器控制**，小6 独有的差异化能力 | 150 MB 下载 |

| **6** | 子智能体 / workflow 编排 | 大 | 长任务扇出 | 中 |

## 七、第 4、5 项实施记录

### 4️⃣ UI 元素树（uiautomation 2.0.29 + comtypes）

**为什么这项重要**：没有元素树时 GUI 操作只能"盲点坐标" ——
要事先知道按钮在 (500,300)，窗口一挪就失效，也没法表达"点那个叫『确定』的按钮"。
接上 UI Automation 后能按**控件名/类型**定位，这是"详细操作程序"与"碰运气点坐标"的分界。

**实测性能（本机）：**
```
GetRootControl()             0.29s
枚举顶层窗口                  0.10s  → 任务栏 / DeepSeek Harness / 豆包 / Program Manager
按类型找控件 searchDepth=6    0.04s
```
所以每次调用都很快，但深度搜索**必须限深限量**（`_UI_MAX=40`，depth≤12）。

**新增方法：**

| 方法 | 作用 |
|---|---|
| `ui_windows()` | 列顶层窗口（名字/控件类型/位置），比 pygetwindow 版更准 |
| `ui_find(name, control_type, window, depth)` | 按名字/类型找控件，只定位不点击 |
| `ui_dump(window, depth)` | 把窗口控件树打成缩进文本 —— 让 AI "看见"界面结构 |
| `ui_click(name, ...)` | 按控件名点击（不依赖坐标） |
| `ui_type(name, text, ...)` | 往指定控件输入（优先 ValuePattern，退化为键盘） |

**自然语言（加在 `parse()` 最前面）**：按名字点比点坐标精确，所以排在坐标类之前
```
点击确定按钮            -> ui_click(name=确定, ButtonControl)
点击名为「取消」的按钮    -> ui_click(name=取消)
看看记事本的控件         -> ui_dump(window=记事本)
列出所有窗口            -> ui_windows
在搜索框里输入 你好       -> ui_type(name=搜索, text=你好)
```

### 5️⃣ 命令执行（严格按草案）

**为什么不用黑名单**：`code_runner` 那套 `["os.system","subprocess","open(","eval(",...]`
有两个毛病 —— ① 字符串黑名单**可绕过**（`getattr(os,"sys"+"tem")`）；
② **误伤正常代码**（`open("a.txt").read()` 直接被杀）。所以反过来做白名单：

| 措施 | 实现 |
|---|---|
| **默认关闭** | 新增规则 `电脑控制.允许命令`，默认 `False` |
| **命令白名单** | 27 个：`dir/type/where/tasklist/whoami/ipconfig/systeminfo/findstr` … 加 `python/py/git/pip/node/npm/pytest/ffmpeg/curl/ping` … |
| **拒绝串联** | 检测到 `&&`、`\|\|`、`\|`、`;`、`>`、`<`、`&`、反引号、`$(`、`%(` 一律拒绝，只允许单条命令 |
| **每条弹窗确认** | 走 `_confirm("执行命令", cmd)`，和删文件同级 |
| **完整日志** | 命令 + 退出码 + 耗时，写 `computer_controller.log` |
| **超时** | 60 秒 |

**开启方式**：`data/rules/rules.json` 里把 `电脑控制.允许命令` 的 `value` 改成 `true`。

> ⚠️ 实施中发现规则**没注册**：第一次测试时 `电脑控制.允许命令` 返回 `(未注册)`，
> 导致 `set()` 无效、命令永远开不起来。已在 `rules_engine` 的 D 组补上注册
> （和 `电脑控制.允许关机` 放一起）。

## 六、第 2、3 项实施记录（文件工具）

### 放在哪个模块？选了扩展 `computer_controller`，没新建模块

`self.whitelist` 才是"AI 能碰哪些文件"的**安全边界**。另起一个 `file_tools`
模块就得复制一份白名单策略 —— 两份策略迟早漂移，而安全边界只该有一处定义。
所以 `fs_read` / `fs_search` / `fs_edit` 统一走 `computer_controller._safe_path()`。

### 三个方法的设计要点

**`read_text(path, start=1, limit=400)`**
- 必须支持只读一段 —— 长文件一次全读进来会直接**塞爆上下文**
- 返回带行号内容（`%5d| 行内容`），为后续 `fs_edit` 定位服务
- 相对路径落到 `<base>/data/`

**`search_text(keyword, path=None, max_hits=60)`**
- 纯 Python（`os.walk` + `re`），**不引入新依赖**
- 跳过 `__pycache__`/`.git`/`node_modules`/`libs`/`backups`/`browsers` 等目录
- 只搜文本扩展名白名单，跳过 >2MB 的大文件
- 返回 `文件:行号: 内容`

**`edit_text(spec)` —— 安全规则是重点**
- `spec` 吃 dict 或 **JSON 字符串**（工具调用只传得进一个参数）
- **`old` 必须在文件里恰好出现一次**：0 次或多次都拒绝
  —— 这是 DSH `edit` 的核心语义，比"整体重写文件"安全得多
- **改前自动备份**到 `data/backups/`；备份失败就放弃修改（不冒险写）
- 空 `old` 直接拒绝（空串会匹配到任何位置）

### 白名单现在可扩展

原来是硬编码 4 个根（项目目录 + 桌面 + 下载 + 文档），`fs_read` 用途很受限。
现在可以在 `data/config.json` 里加：

```json
"文件白名单": ["E:\\projects", "D:\\code"]
```

### 实施中发现的两件事（值得记）

**① 官方 CDN 在国内是断的。**
```
cdn.playwright.dev      ❌ 基础连接已经关闭: 发送时发生错误
cdn.npmmirror.com       ✅ HTTP 200  195.6 MB  269ms
registry.npmmirror.com  ✅ HTTP 200  195.6 MB  160ms
```
第一次 `playwright install chromium` 挂在 0% 好几分钟不动，就是这个原因。
解决办法是设 `PLAYWRIGHT_DOWNLOAD_HOST=https://cdn.npmmirror.com/binaries/playwright`。
**以后重装/换机器都要带上这个变量**，否则会以为"下载卡住了"。

**② tool_caller 只传第一个参数值 —— 这个约束决定了工具入口的形状。**

```python
# tool_caller.call_tools()
arg_val = list(args.values())[0] if args else query
self.trunk.call(info["mod"], info["method"], arg_val)   # ← 只传第 1 个
```

所以工具入口**不能设计成 `(action, **kwargs)`**，必须"收一句话自己解析"。
`computer_controller.try_handle` 就是这个形状，`browser.try_handle` 跟着做了。
以后加多参数工具都要注意这条。

### 实施中修掉的一个连带 bug

`try_handle` 原来的 URL 提取只认 `(?:[\w\-]+\.)+[A-Za-z]{2,6}`，于是：

```
"打开 file:///E:/x/_browser_test.html"
   → file:// 不被识别，反倒匹配到尾巴上的 "_browser_test.html"
   → 补成 https://_browser_test.html → ERR_NAME_NOT_RESOLVED
   → 而且这一失败会把 playwright 的 sync 状态带坏，后续调用报出
     一个**误导性的** "Playwright Sync API inside the asyncio loop"
```

诊断过程值得记：单看那句 asyncio 报错会以为是线程/事件循环问题
（甚至想去给浏览器单开线程），实际是**前一次失败的下游症状**。
改法：先认完整 URL（http/https/**file**），域名 TLD 改用白名单
（`com|cn|net|org|io|dev|...`），免得 `.html` / `.txt` 被当域名。
