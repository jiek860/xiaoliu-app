## 0. 先回答两个问题

### 0.1 工作台的自然语言，现在能像 Trae CN 一样「后台自动写代码/改代码」吗？

**结论：能改代码，但不是 Trae CN 那种「后台自动」——现在是「前台同步 + 逐轮人工审批」。**

拆开看，四件事要分开判断：

| 能力 | 现状 | 证据 |
|---|---|---|
| 自然语言 → 自动收集项目上下文 | **能**（但靠关键词/正则打分，不是语义索引） | `core/code_context.py:90` `build_context(goal, max_files=22, max_chars=24000)`；`core/workspace_index.py:323` `search_text` 用 `re.compile` 扫文件 |
| 自动生成修改并落盘 | **能**，多文件 `update/create/delete/rename/write` | `core/code_agent.py:305` 主循环；`:383` `apply_patch`；`core/patch_engine.py` 支持五种 op |
| 改完自动跑测试/lint、失败回修 | **能**，最多 12 轮 | `core/code_agent.py:408` `run_tests`/`run_lint`；`core/code_agent_policy.py:22` `DEFAULT_MAX_ROUNDS = 12` |
| 备份、回滚、断点续跑 | **能** | `core/code_agent.py:529` `rollback_all`；`core/code_task_queue.py:123` `checkpoint` |
| **真正后台线程执行（UI 不卡）** | **不能** | `gui/workbench_ai_dock.py:275` 在 UI 线程里同步调 `orchestrator.run(...)`；只靠 `:379` `QApplication.processEvents()` 边跑边刷 |
| **无人值守自动应用（不弹审批）** | **不能** | `core/code_agent.py:329-337` 每轮 `approval_cb(patch)`；`gui/workbench_ai_dock.py:392` 弹 `DiffReviewDialog`，关掉就 fail-closed |
| **任务队列自动消费/多任务并行** | **不能** | `core/code_task_queue.py:77` 有 `next_queued()`，但全仓库**没有任何调用方**；`enqueue` 之后是当前这次同步跑，不是排队 |
| **编辑器内选区/函数级改写** | **不能**（编辑器 AI 修复是整文件覆盖） | `gui/code_editor_ai.py:101-118` 要求模型返回完整代码块，`:118` `w.setPlainText(...)` |
| **跨文件语义补全 / 跳转 / 类型诊断** | **不能** | `gui/code_editor_widget.py:125-130` 明确注释「不做 LSP、不跨文件」 |
| **项目约定长期记忆（类似 .trae/rules）** | **不能** | 代码 Agent 提示词是固定字符串 `core/code_roles.py:123-132`，没有读取项目规则文件 |
| **对话式代码问答（解释/定位/影响面）** | **半能** | 有 `/chat` 前缀可切普通对话，但工作台默认 `/code`（`gui/workbench_ai_dock.py:21-33`），代码问答没有专门链路 |

**所以差距不在「能不能改」，而在四件工程化的事**：

1. **执行位置**：从「UI 线程同步」变成「后台 worker + 队列消费」；
2. **自动化档位**：从「每轮必审批」变成「分级自动化（低风险自动应用 + 撤销栈）」；
3. **编辑粒度**：从「整文件覆盖 / 大 patch」变成「局部 hunk + 选区改写 + 编译校验」；
4. **上下文质量**：从「关键词扫文件」变成「符号/调用/测试关系索引 + 语义检索 + 项目约定」。

> 一句话：小6 已有「代码 Agent 的骨架和刹车」，缺的是「后台引擎、自动档、局部编辑、语义大脑」。

#### 与 Trae CN 的能力对照矩阵

| 能力 | Trae CN | 小6 现状 | 差距 |
|---|---|---|---|
| 自动上下文收集 | 语义索引 + 自动 @ | 关键词/正则打分，22 文件/24k 字 | **大** |
| 后台 Agent 执行 | 独立线程/进程，UI 可继续用 | UI 线程同步跑 | **大** |
| 自动应用修改 | Agent 模式可自动 apply，可 review | 每轮弹窗审批 | **大** |
| 多文件 + 终端 + 报错自修复 | 有 | 有（测试/lint/命令白名单） | 小 |
| 编辑器内 Cmd+K 改写 | 有（选区/行内 diff） | 无（整文件替换） | **大** |
| 项目级补全/跳转 | LSP/索引 | 关键字 + 本文件符号 | **大** |
| Plan 模式 | 有 | 有（复杂任务先计划，`core/code_plan.py:58`） | 小 |
| 项目规则文件 | `.trae/rules` | 无 | 中 |
| MCP 工具 | 有 | 有模块（`modules/installed/mcp_client.py`） | 小 |
| 撤销/检查点 | 有 | 有（backup manifest + 断点续跑） | 小 |
| 完全本地/隐私 | 部分 | 本地优先，可全离线 | **优势** |

#### 为什么现在不是「后台」

- `gui/workbench_ai_dock.py` 里 `_run_job` 直接调 `AgentOrchestrator.run`，它是同步阻塞的；事件回调里用 `processEvents()` 让界面「看起来在动」，但模型请求、测试、patch 期间 UI 仍在同一条线程上。
- 仓库里已有现成的 QThread 基建（`gui/workers.py:50` `StreamWorker`、`gui/code_agent_dialog.py:23` `_PrepareWorker`），工作台 AI 面板没有复用它。
- `data/code_jobs/queue.json` 只是「任务台账」，没有常驻 worker 去取 `next_queued()`。
- 审批是模态对话框，弹窗期间任务本身也停住；这既是安全设计，也是「不能后台跑」的直接原因。

### 0.2 需要增加哪些技术栈，让各功能更快更准？

**结论：不需要引入大框架；需要补 6 个「薄能力」，其中 4 个是标准库/Qt 自带，2 个是可选小依赖。**

先给全功能「瓶颈 → 技术 → 收益 → 成本」地图：

| 功能 | 当前瓶颈（证据） | 建议技术 | 收益 | 成本/风险 |
|---|---|---|---|---|
| 对话响应速度 | 人格提示 + 上下文 + 15 条历史一次塞；工作台 `/chat` 分支还没接流式（`core/agent_orchestrator.py` chat 分支 `on_token=None`） | 流式首 token + 稳定提示前缀缓存（Ollama `keep_alive` / 云端 prompt cache）+ 小模型做意图 | 首字 1–2s，长答不空等 | 低（已有 `stream_chat`） |
| 对话准确性 | `is_simple` = 长度≤15 + 关键词（`core/pipeline/context_builder.py:27`）；人格 500 字规则拼接（`core/personality_style_hints.py:204`） | 结构化对话状态 + 回应计划 + 生成后校验（见第 2 章） | 答非所问、重复、AI 腔显著下降 | 中（新模块，默认关） |
| 记忆召回 | 只回填 2–3 条、每条截 100 字（`context_builder.py` 向量/记忆段）；容量 2000（`core/vector_store.py:54`） | 卡片化记忆 + BM25/向量/重排 + 重要度/时新性 | 命中率↑，注入 token↓ | 低（`memory_cards`/`forgetting_curve`/`retrieval` 已有） |
| 工作台自然语言 | 三张词表打分，置信度 <0.45 回落聊天（`core/agent_router.py:87`） | 意图 schema + 槽位抽取 + 规则优先/模型兜底 | 意图准确 ≥92% | 中 |
| 代码上下文 | 关键词扫文件 + 22 文件截断（`core/code_context.py:90`） | 符号/调用/测试图 + 函数级分块 + FTS5（已有 `core/fts_index.py`）+ 可选向量 | 少而准，token -25% | 中 |
| 代码修改准确 | 提示词允许整文件 `write`（`core/code_roles.py:123-132`）；无编译校验 | 局部 hunk 协议 + `ast.parse`/`ruff` 校验 + 影响面测试 | pass@1 +20pp，diff -40% | 中 |
| 补全/跳转 | 只做关键字 + 本文件符号（`gui/code_editor_widget.py:125`） | `jedi`（纯 Python，轻量）或可选 `pyright`/LSP | 跨文件补全、跳转、签名 | 低（jedi ~1MB）/ 中（pyright 需 Node） |
| 索引更新 | 全量 `rebuild`/`refresh` 靠 mtime（`core/workspace_index.py:127`） | `QFileSystemWatcher` 增量 + 后台线程 | 保存即索引，不卡 | 低（Qt 内置） |
| 测试反馈 | 全量跑测试；失败摘要截断（`core/code_agent.py:494`） | 影响面选测（changed files → tests）+ `pytest --lf`/`-x` | 回修轮次 <2，反馈更快 | 低（索引已有 `related_tests`） |
| 语音/实时 | 有 `voice`/`tts`/`realtime_chat` 模块 | 流式 ASR/TTS，情绪参数 | 首包 ≤1.5s | 中（依赖现有） |
| 观测 | `code_events.jsonl` + run registry | 结构化指标（轮次、diff、pass、延迟） | 可验收、可回归 | 低 |

**建议新增依赖（全部可缺省降级）**：

| 依赖 | 用途 | 体积 | 必要性 | 备注 |
|---|---|---|---|---|
| `jedi` | Python 补全/跳转/签名 | ~1–2 MB | **P1 建议** | 纯 Python，无需 LSP 服务 |
| `tree-sitter` + 语言包 | JS/TS/多语言符号 | 视语言包 | P1 可选 | 代码已支持「有则用、无则正则」（`core/symbol_parser.py:57`） |
| `libcst` | Python 结构化改写（保格式） | ~2 MB | P2 可选 | 局部补丁失败时的兜底 |
| `pyright`（Node）或 `mypy` | 类型诊断 | 视安装 | P2 可选 | 失败降级为 ruff + ast |
| `fastembed`/ONNX reranker | 检索重排 | 50–150 MB | P2 可选 | 默认关，CPU 小模型 |
| `pytest-xdist` | 并行测试 | ~100 KB | P2 可选 | 仅在测试多时启用 |

**明确不引入**：LangChain/LlamaIndex（编排已自研，引入会增加黑盒）、`sentence-transformers`/torch（包体几百 MB，与「本地轻量」冲突）、强制 Chroma（现已可选，`core/vector_store.py:66`）、全量微调（成本高、不可控）。

## 1. 总体设计

### 1.1 两条主链路，一个底座

```
用户
 ├─ 聊天窗口 ─────────────► ReplyPipeline（core/pipeline/reply_pipeline.py:41）
 │                          理解 → 检索 → 组装 → 生成 → 后处理
 │
 └─ 工作台自然语言 ───────► TaskService（新）──► AgentOrchestrator
                             ├─ 代码：CodeAgent（探索 → patch → 验证 → 回修）
                             ├─ 电脑：ComputerAgent
                             └─ 对话：trunk.reply
```

两条链路共享四件事：**意图理解、记忆、索引、评测/观测**。方案的核心不是各做各的，而是把「理解」和「记忆」抽成共享底座，避免聊天一套、工作台一套。

### 1.2 五条不变量（任何批次都不能破坏）

1. **可关闭**：所有新能力有开关，默认关闭或影子模式，关掉即回到当前行为。
2. **可回滚**：任何文件修改都先备份，有 manifest，可一键撤销。
3. **可解释**：每次路由/计划/修改都有「为什么」记录（reason + evidence）。
4. **不越权**：路径、命令、网络、审批沿用现有安全层（`core/path_safety.py`、`core/command_policy.py`、`core/agent_permissions.py`、`core/permission_center.py`）。
5. **有度量**：没有基线、没有验收指标的改动不合并。

### 1.3 与 `docs/101` 的关系

`docs/101` 给的是「9 个批次、做什么、验收多少」；本文是它的**详细设计篇**：把「聊天拟人」拆到状态/规划/表达/记忆/反思五层，把「自然语言编程」拆到执行/上下文/规划/编辑/验证/撤销六层，并给出技术栈与文件级落点。两份文档不冲突，101 是路线，102 是实现图。

## 2. 拟人聊天详细方案

### 2.1 现状问题（逐条对应源码）

| # | 问题 | 证据 | 用户感知 |
|---|---|---|---|
| 1 | 「简单/复杂」只看长度和关键词 | `core/pipeline/context_builder.py:27` `len<=15` + `_TRIGGERS` | 短问题被当简单（丢人格），长闲聊被当复杂（塞一堆检索） |
| 2 | 人格是固定规则拼接，封顶 500 字 | `core/personality_style_hints.py:157-204` | 人格像「按剧本演」，换话题就断 |
| 3 | few-shot 是写死的 5 条 | `core/personality_style_hints.py:143-155` | 例子和当前情境无关 |
| 4 | 历史窗口 3/15 条，无摘要 | `core/pipeline/prompt_assembler.py:76-78` | 长对话漂移、忘上文 |
| 5 | 记忆召回 2–3 条、每条截 100 字 | `core/pipeline/context_builder.py` 记忆段；`modules/installed/memory_loop.py:113` | 「你上次说的」经常对不上 |
| 6 | 情绪是关键词触发的 14 种离散心情 | `core/personality_style_hints.py:242`；`update_emotion` | 情绪跳变、不连续 |
| 7 | 群聊角色是「附加发言」 | `core/pipeline/post_processor.py` `merge_group` | 多角色像彩蛋，不是自然多人对话 |
| 8 | 反思只有 1–10 分 + 一句建议 | `modules/installed/self_reflect.py:70-118` | 成长不可验证 |
| 9 | 无「说之前先想」的规划 | 主链路直接组装提示词（`reply_pipeline.py:67`） | 该问的不问、该短的不短 |

### 2.2 目标与验收

**目标**：让用户感觉「在和一个记得住、有分寸、说话像人的朋友聊天」，而不是「一个带人格提示词的问答模型」。

**验收（批次 42 首版 / 批次 49 终版）**：

| 指标 | 口径 | 首版 | 终版 |
|---|---|---|---|
| 拟人度 | 人工 5 分制，双盲 | ≥3.8 | ≥4.2 |
| 人格一致性 | 20 条探针（同一人格在不同话题下的表现） | ≥85% | ≥92% |
| 重复率 | 最近 20 轮 8-gram 重复占比 | <6% | <4% |
| 短问短答 | 用户 ≤8 字时，回复 ≤2 句 | ≥90% | ≥96% |
| 记忆命中 | 问「还记得…」时正确引用 | ≥80% | ≥90% |
| 纠正收敛 | 用户纠正后 1 轮内改对 | ≥80% | ≥92% |
| 首 token | 本地/云端 p95 | ≤1.8s / ≤1.0s | ≤1.2s / ≤0.7s |
| 注入 token | 相对基线 | -15% | -25% |

### 2.3 五层架构

```
用户输入
  │
  ├─ ① 感知层 Perception
  │    文本、时间/地点/天气、情绪词、关系称呼、回复长度期望、是否在忙
  │
  ├─ ② 状态层 DialogueState（本轮 + 跨轮）
  │    意图、话题、用户情绪、关系温度、承诺、未答问题、最近机器人动作
  │
  ├─ ③ 规划层 Planner（先想后说）
  │    回应类型、长度、语气、必须包含、必须避免、引用哪几条记忆
  │
  ├─ ④ 表达层 Renderer
  │    人格卡（稳定）+ 情境提示（可变）+ 记忆卡 + few-shot（检索式）
  │
  └─ ⑤ 校验层 Critic（生成后）
       长度、重复、禁语、AI 腔、是否答非所问、是否过度解释
       └─ 不过 → 一次轻量重写（不重跑整套检索）
```

**关键取舍**：Planner 和 Critic 都用**小模型 + 规则**，不用大模型多次投票。小6 的用户多在本地 7B/4B 模型上跑，多一次大模型调用就是多 5–10 秒，体验直接崩。Planner 在本地模型能力不足时降级为「规则规划器」（见 2.5）。

### 2.4 结构化对话状态（DialogueState）

**目的**：把「靠提示词暗示」变成「显式状态」，让规划、记忆、校验都有依据；同时可持久化、可解释、可测试。

**Schema（草案，存 `data/chat_state.json`，单用户单会话）**：

```json
{
  "version": 1,
  "session_id": "s_20261029_1",
  "updated_at": 1790000000,
  "user": {
    "name": "小刘",
    "relation_stage": "familiar",          // stranger | familiar | close
    "preferences": ["不喜欢被叫您", "晚上写代码"],
    "dislikes": ["长篇说教"]
  },
  "affect": {
    "user_valence": -0.2,                  // -1..1 用户情绪
    "user_arousal": 0.6,                   // 0..1 激动程度
    "bot_valence": 0.3,
    "bot_energy": 0.7,                     // 0..1 精力
    "trust": 0.55,                         // 0..1 关系信任
    "warmth": 0.5                          // 0..1 亲密度
  },
  "topic": {
    "current": "代码调试",
    "recent": ["工作", "代码调试"],
    "switched_at": 1790000000
  },
  "turn": {
    "intent": "request_help",              // smalltalk|request_help|vent|ask_fact|correct|play|silence
    "expects": "short_action",             // short_action|explanation|comfort|question_back
    "user_brevity": "short",               // short|normal|long
    "unanswered": ["用什么模型"],
    "bot_last_acts": ["comfort", "answer"] // 最近 3 次机器人动作，用于去重
  },
  "commitments": [
    {"text": "明天提醒他交周报", "due": "2026-10-30T09:00", "status": "open"}
  ],
  "open_questions": [
    {"text": "你想先修哪个报错？", "asked_at": 1790000000}
  ]
}
```

**更新规则（规则优先，模型可选）**：

| 字段 | 规则来源 | 模型兜底 |
|---|---|---|
| `intent` | 问号/祈使/情绪词/纠错词（「不对」「我是说」） | 小模型 3 分类 |
| `expects` | 「怎么/为什么」→ 解释；「帮我」→ 动作；「烦/累」→ 安慰 | 小模型 |
| `user_brevity` | 字符数 ≤8 短 / 9–40 正常 / >40 长 | 不需要 |
| `affect` | 情绪词表 + 标点 + 感叹号密度，做 EMA 平滑 | 小模型可选 |
| `relation_stage` | 交互天数 + 消息数 + 用户称呼 | 不需要 |
| `topic` | 关键词 + 向量相似度；连续 2 轮不同则切换 | 不需要 |
| `commitments` | 正则「明天/记得/提醒我」+ 时间解析 | 小模型可选 |

**降级**：状态文件损坏/不存在 → 用默认值；所有更新失败都吞掉（silent 0 规则），但不能让回复失败。

### 2.5 回应规划层（ResponsePlanner）

**输出是一份「说话前的小纸条」**，不是自然语言：

```json
{
  "act": "answer_with_action",     // answer|ask_back|clarify|comfort|tease|refuse|ack
  "length": "short",               // 1句|2-3句|可展开
  "tone": "轻松但认真",
  "must_include": ["先给结论", "再给一步操作"],
  "avoid": ["不要说'作为AI'", "不要复述用户问题", "不要列 5 条"],
  "memory_refs": ["m_1024", "m_2048"],
  "persona_beats": ["偶尔自嘲", "不用您"],
  "question_back": true            // 需要反问时最多 1 个
}
```

**决策表（规则版，默认路径）**：

| 用户状态 | act | length | 备注 |
|---|---|---|---|
| 短问候/短回应 | `ack` | 1 句 | 禁止展开 |
| 明确求助 + 简单问题 | `answer` | 1–2 句 | 先结论 |
| 明确求助 + 复杂问题 | `answer` | 可展开 | 分点但 ≤3 |
| 情绪倾诉 | `comfort` | 1–2 句 | 先共情，不解决问题 |
| 用户纠正 | `ack` + 修正 | 1 句 | 立刻认错，不解释 |
| 信息不足 | `clarify` | 1 句 + 1 问 | 只问一个最关键槽位 |
| 越界/危险请求 | `refuse` | 1–2 句 | 给替代方案 |
| 连续 3 轮同一问题 | `ack` + 提醒 | 1 句 | 「这个我们聊过啦」 |

**模型版（可选）**：小模型输入「用户原话 + 状态摘要 + 最近 4 轮」，输出上面 JSON。只在 `chat.planner=model` 时启用；失败或超时 800ms 直接回退规则版。

**为什么先规划**：现在的模型被要求「短句口语、一两句说完」，但同时又被塞了 500 字人格 + 15 条历史 + 检索结果，模型会优先服从「信息完整」，导致越答越长。把长度、语气、禁止项单独抽出来，作为**强约束**放在提示词最后一段，服从率明显更高。

### 2.6 人格系统 v2：分层人格卡

现在的问题是「所有规则挤在 500 字里」，结果是稳定人格和不稳定情境互相挤占预算。v2 拆成四层，各自有 token 预算：

| 层 | 内容 | 预算 | 更新频率 |
|---|---|---|---|
| L1 核心人格 | 身份、价值观、说话铁律、绝对禁止 | ~180 字 | 几乎不变 |
| L2 关系状态 | 称呼、亲疏、最近互动、承诺 | ~120 字 | 每轮可更新 |
| L3 情境提示 | 时间/天气/深夜/情绪/吐槽/安慰 | ~150 字 | 每轮变化 |
| L4 禁语与风格 | 禁用词、句式偏好、emoji 预算 | ~80 字 | 版本化配置 |

**总量 ≤550 字**（现在 500 字上限保留，但分配可控）。L1 保持稳定，有助于「人格一致性」；L3 才随情境变，避免人格整体漂移。

**禁语表（`data/persona_banned.json`，版本化）**：
- AI 腔：`作为AI`、`我无法`、`希望对你有所帮助`、`首先/其次/最后`（连续出现时）、`总之`、`需要注意的是`；
- 过度服务：`请问还有什么可以帮您`、`如果您需要`；
- 说教：`你应该`、`你必须`、`别难过`（→ 改成「我在」）；
- 空话：`这取决于很多因素`、`因人而异`（没有下文时）。

**few-shot 检索化**：把现在写死的 5 条扩成 60–100 条「情境-回复」对，按 `intent + topic + tone` 检索 2–3 条注入，而不是固定 5 条。冷启动仍用现有 5 条兜底。

### 2.7 表达层：去模板、去 AI 腔

生成后做**规则校验 + 一次轻量重写**，不重跑检索：

| 检查 | 规则 | 处理 |
|---|---|---|
| 超长 | `length=short` 但 >2 句 / >60 字 | 截断到前 2 句或重写 |
| 复述问题 | 开头 6 字与用户问题重合 | 删掉开头 |
| 重复 | 与最近 5 条回复 8-gram 重合 >0.6 | 换说法（同义改写模板） |
| 禁语 | 命中禁语表 | 替换/删除 |
| 排比式列点 | 连续 3 个「1. 2. 3.」 | 合并成 2 句 |
| emoji 过多 | >2 个 | 保留 1 个 |
| 反问过多 | >1 个问号 | 保留 1 个 |
| 答非所问 | `expects=short_action` 但没给动作 | 补一句「先试这个：…」 |

**重写策略**：规则版（删句、换词、合并）优先；规则改不动时，`chat.critic_rewrite=true` 才调一次小模型重写，且只给「原文 + 问题清单」，不给上下文，保证快。

### 2.8 情绪与关系：从离散心情到连续状态

现在 `update_emotion` 是关键词 → 14 种心情（`core/personality_style_hints.py:242`），问题是跳变。v2 改为：

- **连续维度**：`valence`（-1..1）、`arousal`（0..1）、`energy`（0..1）、`trust`（0..1）、`warmth`（0..1）；
- **事件驱动更新**：用户夸 → trust/warmth 小升；用户骂 → valence 降、warmth 略降；深夜 → energy 降；连续高强度写代码 → energy 降、arousal 升；
- **指数平滑**：`new = old * 0.8 + event * 0.2`，避免跳变；
- **向基线回归**：每小时向基线缓动 5%，避免长期阴郁；
- **展示映射**：保留 14 种「心情名」用于界面和提示词，但由连续值映射，不再直接由关键词决定；
- **关系阶段**：`stranger → familiar → close`，由天数/消息数/称呼触发，影响称呼与玩笑尺度。

**验收**：同一段对话里，情绪不应在相邻两轮从「开心」跳到「生气」；人工抽检情绪连续性 ≥90%。

### 2.9 记忆 v2：复用现有资产，不重造

小6 其实已经有四套记忆资产，问题是**各管一段、没有统一入口**：

| 现有资产 | 作用 | 证据 |
|---|---|---|
| `modules/installed/memory_cards.py` | 规则触发 → 卡片提取 → Jaccard 去重 | `:20` 类；`:38-50` 规则与信号 |
| `modules/installed/forgetting_curve.py` | 间隔重复、复习提醒 | `:14` 类；`:28` 间隔 [1,3,7,15,30] |
| `core/vector_store.py` | SQLite + numpy 向量检索（可选 Chroma） | `:24`；`:54` 容量 2000；`:66` Chroma 可选 |
| `modules/installed/memory_loop.py` | 情景记忆 + 召回 | `recall` 取向量 + 情景 |
| `core/retrieval.py` | BM25 + 向量 RRF + 词面重排 | `:126` `search` |

**v2 做的事**：统一 schema + 统一召回 + 统一注入预算。

**卡片 schema**：

```json
{
  "id": "m_1024",
  "type": "preference",          // fact|preference|event|commitment|relationship
  "text": "用户不喜欢被叫「您」",
  "subject": "user",
  "confidence": 0.9,
  "importance": 0.8,             // 0..1
  "created_at": 1790000000,
  "last_used_at": 1790000000,
  "source": "chat",
  "expires_at": null,
  "conflicts_with": []
}
```

**写入策略**：
- 强信号（「我喜欢/我讨厌/记住/以后」）立即写；
- 普通对话每 5 轮总结一次（沿用 `memory_cards` 的 `min_rounds`）；
- 承诺类必须带 `due`，进入 `commitments`；
- 敏感信息（身份证、密码、密钥）**不落卡**，只记「有这类信息」的标记。

**召回排序**：

```
score = 0.45 * 相关度(BM25/向量 RRF)
      + 0.25 * importance
      + 0.20 * 时新性(半衰期 60 天，沿用 vector_store.half_life)
      + 0.10 * 关系/话题匹配
```

**注入预算**：最多 3 张卡 + 每张 ≤1 行事实，总 ≤200 字；同一张卡 24 小时内不重复注入；连续两轮注入同一张卡则降权。

**冲突消解**：
- 偏好冲突：新卡覆盖旧卡（保留历史版本）；
- 事实冲突：高置信度优先；接近则反问一次「你之前说 A，现在改成 B 了？」；
- `expires_at` 到期自动失效（如「这周在出差」）。

**用户可见**：复用现有 `gui/memory_view_dialog.py`，增加「记得的你」列表，可删除/纠正/导出。

### 2.10 反思与成长 v2

现在：1–10 分 + 一句建议 + 50 条历史 + 低于 6 分回注（`modules/installed/self_reflect.py:70-161`）。

v2：
1. **多维评分**：准确 / 贴合（是否答到点上）/ 人格 / 有用 / 长度，各 1–5，规则 + 小模型；
2. **失败用例库**：低分样本进 `data/chat_failures.jsonl`，作为回归集（不是只看分数）；
3. **建议晋升**：同一类建议出现 ≥3 次 → 生成候选规则，进「待确认」；用户确认后写入禁语/风格规则（可审计、可撤销）；
4. **周报**：本周对话数、平均分、最差 3 条、改进项、已生效规则；
5. **不做**：自动改人格、自动改代码——只提议，不自动执行。

### 2.11 主动性与群聊、语音

- **主动性**：现有 `personality.py` 有「一天最多搭一次」的雏形（`last_proactive_date`）。v2 改为**事件驱动**：任务完成、检测到报错、承诺到期、用户长时间沉默；保留每日 1 次预算、免打扰时段、一键关闭。
- **群聊**：`group_chat.start_roles` 现在与主回复并行（`reply_pipeline.py:73-79`），但角色发言是「附加」。v2 给角色也加状态（谁在说、说到哪、是否被点名），并限制总条数，避免刷屏。
- **语音**：复用 `voice`/`tts`/`realtime_chat`；情绪参数映射到语速/音高；首包 ≤1.5s；本地失败降级为文字。

### 2.12 延迟预算与降级

| 阶段 | 预算 | 降级 |
|---|---|---|
| 状态更新 | 30ms | 规则版，失败用默认 |
| 记忆召回 | 300ms | 只走 BM25（向量超时 5s 不可等） |
| 规划 | 800ms（模型版） | 回退规则决策表 |
| 生成首 token | 1.2s 本地 / 0.7s 云端 | 非流式则先显示「在想…」 |
| 校验 | 20ms | 只做规则 |
| 重写 | 1.5s | 只做截断/删句 |

**总预算**：简单问题 ≤2s 见完整回复；复杂问题首 token ≤1.5s，其余流式。

### 2.13 评测（必须先行）

现有评测只有 20 条安全/工具链用例（`tests/eval/cases.json`），**没有对话质量基准**。v2 需要：

1. **Golden set**：200 条中文对话，覆盖闲聊/求助/情绪/纠正/记忆/边界；每条带「期望要点」而非唯一答案；
2. **Pairwise 盲测**：旧版 vs 新版，人工或 LLM 裁判，胜负 + 理由；
3. **人格探针**：20 条固定问题在不同话题下问，检查是否仍符合人格；
4. **重复率/长度/禁语**：纯规则，可 CI；
5. **回归**：失败用例库进 CI，低分复现率必须下降。

## 3. 自然语言自动编辑/修改代码详细方案

### 3.1 现状链路（逐段有证据）

```
工作台输入框（gui/workbench_ai_dock.py:195 start）
  → enqueue 到 data/code_jobs/queue.json（:210-216）
  → _run_job（:221）同步创建 AgentOrchestrator（:235-246）
  → orchestrator.run（:275）—— 仍在 UI 线程
      → CodeAgent.run（core/code_agent.py:198）
          → git_protect（:235）
          → build_context（core/code_context.py:90，22 文件/24k 字）
          → confirm_plan（core/code_plan.py，复杂任务先计划）
          → 每轮：propose_patch（探索 6 轮 → 修改 4 轮）
                  → 审批（DiffReviewDialog）
                  → dry_run_patch
                  → apply_patch（backup）
                  → run_tests + run_lint
                  → evaluate_round（失败指纹/轮次上限）
          → 成功 / 失败 / 取消 / 回滚
```

**能跑通的闭环已经不错**，真正卡住「像 Trae CN」的是五个结构性点：

1. **执行在 UI 线程**：`gui/workbench_ai_dock.py:275` 同步调用，只有 `processEvents`；模型一卡，窗口就卡。
2. **每轮强制审批**：`core/code_agent.py:329-337`；模态弹窗期间任务停住。
3. **无队列 worker**：`next_queued()`（`core/code_task_queue.py:77`）无人调用。
4. **上下文靠词频/正则**：`core/workspace_index.py:323` 是 `re.compile` 扫文件；`core/code_context.py:90` 按目标词打分挑 22 个文件。
5. **编辑粒度偏大**：提示词允许 `write` 整文件（`core/code_roles.py:123-132`）；编辑器 AI 修复直接 `setPlainText`（`gui/code_editor_ai.py:118`）。

### 3.2 目标形态：Trae CN 对齐 + 本地差异化

**对齐**：后台执行、自动档、局部编辑、语义索引、行内改写、项目规则。

**差异化（不照抄）**：
- **本地优先**：默认本地模型可跑通；云端只是加速；
- **隐私**：代码不出本机是默认值；
- **可回滚**：每个 patch 有 manifest，随时撤销；
- **可解释**：每个计划/修改都有理由与证据文件；
- **不偷偷跑**：自动档只对「低风险 + 可撤销」开放，高风险仍审批。

### 3.3 自动化分级（默认 L2）

| 级别 | 行为 | 适用 | 默认 |
|---|---|---|---|
| L0 手动 | 只给建议，不落盘 | 高风险重构、删文件 | — |
| L1 建议 | 生成 diff，用户点应用 | 现有行为 | — |
| L2 半自动 | 低风险改动自动应用，高风险弹窗；全程可撤销 | 默认 | ✅ |
| L3 自动 | 计划确认后，后续轮次自动应用 + 测试 + 回修，不逐轮弹窗 | 用户显式开启 | 开关 |
| L4 后台代理 | 监听任务/报错/文件变化，自动起任务 | 远期 | 不做默认 |

**风险分级规则**（决定是否自动应用）：

| 操作 | 风险 | L2 行为 |
|---|---|---|
| 新建文件（不在受保护目录） | 低 | 自动应用 |
| 新增测试文件 | 低 | 自动应用 |
| 修改单个函数/≤40 行 | 中 | 自动应用 + 顶部提示，可撤销 |
| 跨 ≥3 文件 / >120 行 | 高 | 弹窗审批 |
| 删除/重命名文件 | 高 | 弹窗审批 |
| 修改配置/依赖/构建脚本 | 高 | 弹窗审批 |
| 触碰 `.git`/`data`/`backups` | 禁止 | 直接拒绝（`core/patch_engine.py:26` 已保护） |

### 3.5 后台执行（最关键的一步）

**现状**：同步 + `processEvents`。

**目标**：
1. **单例 TaskService**：持有 `QThread`（复用 `gui/workers.py` 模式），信号回 UI；
2. **单写者锁**：同一工作区同一时刻只允许一个写任务，避免两个 agent 互相覆盖；
3. **队列消费**：`TaskService` 启动时取 `next_queued()`，按顺序跑；失败/取消/中断保留断点（`checkpoint` 已有）；
4. **UI 不阻塞**：所有事件经信号回主线程；编辑器刷新只在 `applied` 事件后做；
5. **取消语义**：`cancel()` 立即置位 `CancelToken` + 杀子进程（`core/code_agent.py:84-127` 已有），UI 立刻恢复可用；
6. **进程隔离（可选）**：模型调用与测试放到独立进程，崩溃不拖垮主程序；先做线程版，观察稳定性再升级。

**验收**：任务运行中，用户可以在工作台继续编辑、切换文件、发消息；取消后 1s 内 UI 恢复。

### 3.8 编辑协议 v2（局部优先）

现状：`_MODIFY_SYSTEM`（`core/code_roles.py:123-132`）允许 `write` + `content`；`patch_engine` 有 `hunks` 但模型倾向整文件。

v2 协议约束：

1. **已存在文件禁止 `write`**：只允许 `update` + `hunks`；`write` 仅用于新建；
2. **hunk 必须唯一**：`old` 在文件中唯一（已有 `_locate_exact`，`core/patch_engine.py:101`）；不唯一 → 自动扩上下文重试 1 次；
3. **行号锚点可选**：模型给 `line` 时优先按行号定位，再校验内容；
4. **语法校验**：Python 改完 `ast.parse`；JS/TS 有 `tsc --noEmit` 才用；失败即回修，不落盘；
5. **最小性**：单文件 diff >200 行或跨 >5 文件 → 拒绝并提示拆分；
6. **JSON Schema 约束**：模型支持时强制 `format=json`（`core/model_capabilities.py:13` 已有 `json_mode` 能力位），不支持则解析后校验；
7. **禁止路径**：沿用 `core/patch_engine.py:26` `PROTECTED_PARTS`；
8. **并发保护**：`base_hash` 已存在（`core/patch_engine.py:174` 校验、`core/code_explorer.py:49` 自动填充），v2 在 apply 前再校验一次，文件被用户改过则放弃本轮。

**目标指标**：平均 diff 行数 **-40%**；无关文件改动率 **<10%**；大文件（>1000 行）修复成功率 **≥80%**（不再整文件覆盖）。

## 4. 技术栈落地清单

### 4.1 必加（P0，批次 41–46）

| 技术 | 解决 | 依赖 | 落地方式 |
|---|---|---|---|
| QThread + TaskService | UI 卡顿、无后台 | Qt 自带 | 复用 `gui/workers.py` 模式 |

| 影响面选测 | 回修慢、全量测试慢 | 已有索引 + coverage | `tests_for` + `related_tests` |
| 增量索引（QFileSystemWatcher） | 保存后索引过期 | Qt 自带 | 后台 debounce 1s |

### 4.2 可选（P1/P2）

| 技术 | 解决 | 体积/成本 | 默认 |
|---|---|---|---|
| `jedi` | Python 补全/跳转 | ~1–2 MB | 关闭，设置里开 |
| `pyright`/`mypy` | 类型诊断 | 中 | 关闭 |
| `tree-sitter` 语言包 | JS/TS 符号 | 中 | 有则用 |
| `libcst` | 结构化改写 | ~2 MB | 关闭 |
| `fastembed`/ONNX reranker | 检索重排 | 50–150 MB | 关闭 |

| `watchdog` | 跨平台文件监听 | 小 | 不需要（Qt 已够） |

### 4.3 不加

- LangChain / LlamaIndex：编排已自研，引入黑盒与版本耦合；

- 全量微调：不做默认；最多离线 LoRA 实验；

## 9. 一页结论

1. **现在能自动改代码，但不是后台**：工作台是「UI 线程同步 + 每轮审批」；后台执行、队列消费、自动档、局部编辑、语义索引，这五件事是「像 Trae CN」的真正门槛。
2. **不需要大框架**：QThread、FTS5、JSON Schema、`ast`+`ruff`、影响面选测都是现有能力或标准库；`jedi`/tree-sitter/reranker 全部可选、可降级。
3. **聊天先做「状态 → 规划 → 校验」三层**：比继续堆人格提示词更划算；记忆复用现有四套资产，统一 schema 和召回即可。
4. **代码先做「后台 + 局部 + 验证」**：这是收益最大、风险可控的三刀；自动档默认只对低风险开放。
5. **先评测再改**：没有基线，所有「更拟人/更准确」都无法证明；批次 41 必须先落地。
