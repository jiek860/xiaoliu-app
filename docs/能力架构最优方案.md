# 小6 能力架构最优方案

> 目标：让 47 个模块**既能"说一句就用"，又保留按钮的可发现性**，
> 同时把原语层加厚到能应付没打包过的长尾任务。
>
> 结论先说：**不选豆包也不选 DSH，走分层——原语做地基、技能做固化层、按钮降级为快捷键。**
> 而落地的支点是一个**已经存在但没被用起来的东西**：签名清单 `manifest.json`。

---

## 一、诊断：小6 现在是"两头不靠"

实测数据（2026-10-13）：

| 指标 | 实测值 | 说明 |
|---|---|---|
| 登记模块 | 72 个 | LAZY_MAP |
| **能靠说话触发的** | **7 个（10%）** | 只在 `tool_caller` 的 19 个工具里 |
| 只有 GUI 入口的 | 8 个 | 翻译/TTS/语音/插件市场/人格引擎… |
| **静态扫不到调用点的** | **44 个** | 天气/待办/笔记/日历/OCR… 只能靠人点 |
| GUI 控件创建 | 114 处 / 27 文件 / 14 弹窗 | — |
| 手写的 `ACTIONS` 入口表 | 24 条 | `gui/module_tools_dialog.py` |

**最刺眼的证据**——工具面板跑模块时要猜参数：

```python
# gui/module_tools_dialog.py:263
fn = getattr(m, meth)
for args in ((), (7,), (30,), (20,)):    # 猜！试到不报 TypeError
    try: return fn(*args)
    except TypeError: continue
```

而 `tool_caller` 的 19 个工具**全部声明了 `args`**（19/19），所以它们能被模型统一调用。

> **根因一句话**：模块没有统一的接口声明（schema）→ 模型调不动它们 →
> 只能人工写一张 `ACTIONS` 表、一个功能配一个按钮。

这不是"功能多所以按钮多"，是**"功能没有可调用的声明所以必须配按钮"**。

## 二、目标形态

```
                        ┌──────────────────────────────┐
   用户 ──┬─ 说一句话 ──→│  模型自主编排（技能 + 原语）      │
          │              └──────────────────────────────┘
          ├─ Ctrl+K ────→  命令面板（可搜索、可发现）
          │
          └─ 点按钮 ────→  快捷键（保留可发现性，不再是唯一入口）
```

**三条路通向同一个能力**，而不是每个能力各配一个按钮。

## 三、落地的支点：把"签名清单"升级成"能力清单"

### 为什么是这个支点

`modules_repo/manifest.json` **已经**为 47 个模块声明了 13 个字段：

```
name  title  file  cls  desc  group  version
button  needs_model  depends  size  sha256  signature
        ↑ 侧边栏按钮就藏在这里，说明"清单驱动 UI"这条路已经通了
```

而且：

| 现成条件 | 位置 | 意义 |
|---|---|---|
| 运行时已经在读它 | `core/module_buttons.py` | 加载路径现成，不用新写 |
| 它是**唯一**元信息来源 | 同文件 docstring 明说 | 不会有两个真相 |
| 它是 **RSA 签名的** | `tools/sign_modules.py` | 能力声明**防篡改** |
| 重建时保留元信息 | `tools/rebuild_modules_repo.py` 的 `om or mm` | 加字段能自动存活 |
| 有干净的加载器可参照 | `module_buttons.load_buttons()` 75 行、不依赖 Qt、可单测 | 直接照抄结构 |

### 具体做法：加一个 `tools` 字段

```json
{
  "name": "weather",
  "title": "天气查询",
  "desc": "天气查询：问天气时联网取",
  "button": null,
  "tools": [
    {
      "name": "weather_now",
      "method": "get",
      "desc": "查某个城市现在的天气",
      "args": {"city": "城市名，如：杭州"},
      "readonly": true,
      "confirm": false
    }
  ],
  "sha256": "...", "signature": "..."
}
```

然后：

```
modules/installed/weather.py  ──声明 TOOLS──┐
                                            ↓
tools/rebuild_modules_repo.py  ──写进清单──→ manifest.json ──→ sha256+签名
                                                            ↓
core/module_caps.py  ──读清单（照 module_buttons 的模式）──┐
                                                          ↓
modules/installed/tool_caller.py  ──内置工具 + 清单工具──→ LLM 可调用的完整工具表
                                                          ↓
                                            模型能按需调用这 47 个模块
```

**关键收益**：
- 模块**自己声明**能力（单一真相，不再手工维护 `ACTIONS` 表）
- 声明**带签名**（防篡改，且市场分发时自动带上）
- 现有基建**全部复用**（loader 模式、rebuild、sign 签名链）

**兼容策略**：模块没声明 `TOOLS` 的，清单里就是 `[]`，`tool_caller` 只用内置工具 —— 
**不声明不报错，声明了才生效**，可以一个一个模块慢慢补。

## 四、五层架构

| 层 | 内容 | 现状 | 要做什么 |
|---|---|---|---|
| **L1 原语层** | `fs_read/search/edit` `browser` `ui_*` `shell` `code_run` | ✅ **本轮已加厚** | 补 `glob`（按模式找文件）；`shell` 已白名单化 |
| **L2 技能层** | 47 个模块 | ⚠️ 只有 7 个可调用 | **补 `TOOLS` 声明 → 进清单 → 模型可调用**（本方案重点） |
| **L3 入口层** | 按钮 / 面板 / 命令面板 | ⚠️ 114 处控件、无命令面板 | 命令面板（Ctrl+K）；按钮降级为快捷键 |
| **L4 安全层** | `readonly` / `confirm` / `danger` 三级 | ⚠️ 只有 `_confirm` 一刀切 | 按 `tools` 声明分级；沿用规则引擎开关 |
| **L5 模式层** | 日常 / 干活 / 编程 | ❌ 没有 | 每个模式暴露不同工具子集（学 DSH 的 preset + 豆包的"工作任务"） |

### L4 安全分级（学豆包按能力隔离）

豆包的虚拟桌面之所以能"不干扰你"，是因为**"操作电脑"是一个被封装的技能**，
所以能给它单独开沙箱。小6 的 `tools` 声明正好提供了同样的切分点：

```json
{"name": "weather_now", "readonly": true,  "confirm": false}   // 只读，直接跑
{"name": "clean_all",   "readonly": false, "confirm": true }   // 写数据，弹窗
{"name": "shutdown",    "danger": true,    "confirm": true }   // 危险，规则引擎默认关
```

### L5 模式层（学 DSH 的 preset）

```python
PRESETS = {
    "日常": ["vector_search", "graph_query", "weather_*", "todo_*", "notes_*"],
    "干活": ["fs_*", "browser", "shell", "ui_*", "code_run", "task_plan"],
    "编程": ["fs_*", "code_run", "shell", "browser", "glob"],
}
```

好处：**工具表变小 → 模型选错率下降 → 提示词变短**。
这同时解决了"原语多了以后模型挑花眼"的问题（DSH 用 `preset-minimal` 就是这个思路）。

## 五、实施路线（六批，每批独立可验证）

| 批次 | 做什么 | 产出 | 验收 |
|---|---|---|---|
| **1** | **能力清单基础设施**：`tools` 字段 + `core/module_caps.py` + `tool_caller` 接入 + rebuild/sign 覆盖 | 机制通了，但清单里还是空的 | 手工在清单里加一条 → 模型能调到它 |
| **2** | **高频模块补声明**（先 10 个） | 10 个模块从"只能点"变"能说" | 每个都能靠说话触发 |
| **3** | **命令面板**（Ctrl+K） | 可搜索的统一入口 | 输入关键词能跳到任意能力 |
| **4** | **按钮降级** | 撤掉一批重复入口 | 按钮数明显下降且没丢功能 |
| **5** | **安全分级** | `readonly/confirm/danger` 生效 | 危险能力默认关 |
| **6** | **模式/预设** | 日常/干活/编程 | 工具表随模式变化 |

### 批次 2 的候选模块（按"高频 + 接口简单 + 现在够不着"筛）

| 优先级 | 模块 | 现状 | 理由 |
|---|---|---|---|
| 🔴 高 | `weather` 天气 | **0 个调用点** | 最高频的日常问答，现在完全够不着 |
| 🔴 高 | `todo` 待办 / `notes` 笔记 | **0 个调用点** | 高频个人助理功能 |
| 🔴 高 | `calendar` 日历 | **0 个调用点** | 同上 |
| 🔴 高 | `image_ocr` 图片识别 | 只在 `ACTIONS` 表里 | 有明确输入输出，好声明 |
| 🟡 中 | `translate` 翻译 | 只有 GUI | 极高频，接口最简单 |
| 🟡 中 | `memory_organizer` / `memory_archiver` | 只在 `ACTIONS` 表里 | 记忆整理，用户会想"帮我整理下记忆" |
| 🟡 中 | `stats_report` / `mood_report` / `growth_report` | 只在 `ACTIONS` 表里 | "给我看看统计" |
| 🟢 低 | `group_chat` 群聊 / `skill_distill` 技能沉淀 | 有程序调用点 | 已有内部路径，补个对话入口 |

## 六、备选方案对比（为什么不选它们）

| 方案 | 做法 | 为什么否掉 |
|---|---|---|
| **A. 全原语化**（纯 DSH 路线） | 47 个模块砍成十几个原语 | 小6 面向的是"点一下就用"的场景；且**删功能不是优化** |
| **B. 全技能化**（纯豆包路线） | 继续加按钮、技能封闭 | 丢掉长尾能力；按钮维护成本已经显形（26 个按钮裁字） |
| **C. 维持现状** | 只修 bug、加按钮 | "两头不靠"的问题原样保留 |
| **D. 本方案：分层** | 原语地基 + 技能固化 + 清单驱动 + 按钮降级 | ✅ **两头都占**：能说、能点、能组合、可扩展 |

## 七、这个方案和"豆包 / DSH"的对应关系

| 学到什么 | 来自 | 在小6 怎么落 |
|---|---|---|
| 技能要能被模型**统一调用** | DSH（工具都有 schema） | `manifest.tools` 声明 |
| 技能要**可发现** | 豆包（有技能列表） | 命令面板 + 按钮保留 |
| 危险能力要**能按技能隔离** | 豆包（虚拟桌面沙箱） | `tools` 的 `readonly/confirm/danger` 分级 |
| 原语要能**组合出长尾** | DSH（19 个原语） | L1 已加厚（`fs_*`/`browser`/`ui_*`/`shell`） |
| 工具多了要**按场景收窄** | DSH `preset-*` + 豆包"工作任务"模式 | L5 模式/预设 |

**一句话**：**机制学 DSH（schema 驱动、原语组合），产品学豆包（技能可发现、危险可隔离），
支点用小6 自己已经有的签名清单。**

---

## 八、为什么先做批次 1

因为它**不改任何现有行为**，却把后面五批的地基铺好：

- 模块不声明 `TOOLS` → 清单为空 → 行为与现在**完全一致**
- 声明了 → 立刻能被模型调用（并且是签名保护的）
- 之后补模块、加命令面板、做分级、加模式，**全都在这个机制上长出来**

风险最低、收益最持久的一步。
