# 小6 能力架构最优方案 v3（已验证版）

> **v2 有一个技术阻塞没发现**：`tool_caller` 分发时**只传第一个参数值**，
> 所以 v2 里写的多参数声明（`{"topic":…, "rounds":…}`）**根本传不进去**。
> v3 先修这个阻塞（已实测 **8/8 通过 + 向后兼容**），再往下走。
>
> v3 另外补了两件事：
> - **实测证明**那 24 条能力真的能调用（12 个只读真跑通，抓到并修掉 1 个潜伏 bug）
> - **工具预算**：能力从 19 涨到 42 时提示词会涨 2.1 倍，必须做两级筛选

## 二、🔴 v2 的阻塞：分发只传第一个参数

```python
# modules/installed/tool_caller.py:188（现状）
arg_val = list(args.values())[0] if args else query
r = self.trunk.call(info["mod"], info["method"], arg_val)   # ← 只传第 1 个
```

**后果**：v2 里这些声明全都传不对 ——

| 声明 | 现状会发生什么 |
|---|---|
| `debate(topic, rounds)` | 只传 topic，rounds 用默认值 |
| `chat_vote(message, models)` | 只传 message |
| `export_encrypted(out_path, password)` | 只传 out_path → **必填 password 缺失 → 抛异常** |

### 修法（已实测 8/8 通过，且向后兼容）

```python
def dispatch(trunk, mod, method, args, query=""):
    """统一分发器：按签名决定 kwargs 还是 first-arg

    先看声明里的参数名是否都在方法签名里 —— 都在就按 kwargs 传（支持多参数），
    否则退回"只传第一个值"（保持对现有 19 个工具的兼容）。
    """
    t.call(mod, "__no__")
    m = trunk.modules.get(mod)
    if m is None:
        return {"ok": False, "错误": "模块没加载"}
    fn = getattr(m, method, None)
    if fn is None:
        return {"ok": False, "错误": "方法不存在"}
    try:
        names = [p.name for p in inspect.signature(fn).parameters.values()
                 if p.kind in (p.POSITIONAL_OR_KEYWORD, p.KEYWORD_ONLY)]
    except Exception:
        names = []
    if args and all(k in names for k in args):
        return {"ok": True, "mode": "kwargs", "结果": fn(**args)}
    val = list(args.values())[0] if args else query
    return {"ok": True, "mode": "first-arg",
            "结果": fn(val) if (args or query) else fn()}
```

### 🐛 顺带抓到一个潜伏 bug（已修）

```python
# core/memory_organizer.py:check_conflicts（原文）
for ln in open(self.cards_path, encoding="utf-8")[-200:]:   # ← 文件对象不能切片！
```

`open()` 返回的文件对象**不支持切片**，`[-200:]` 必然抛
`TypeError: '_io.TextIOWrapper' object is not subscriptable` ——
**「查记忆冲突」这个功能从来没成功过一次**（作者本意是"读最后 200 行"）。
已修成 `f.read().splitlines()[-200:]`，现在返回 `{'冲突数': 0, '冲突': []}`。

> **这条本身就是方案的一个论据**：这 24 个功能只能靠人点按钮，所以坏了没人发现。
> **一旦能被"说一句"触发，坏掉会立刻暴露。**
> → 所以**每批的验收必须是"逐个真跑"**，不能只看"声明写好了"。

## 四、🆕 工具预算：能力变多后提示词会撑爆

实测 `_llm_decide` 的提示词大小：

| 工具数 | 提示词 | 倍数 |
|---|---|---|
| 19（现状） | 1 213 字符 | 1.0x |
| 30 | 1 843 | 1.5x |
| **42**（+24 条能力） | **2 531** | **2.1x** |
| 60 | 3 562 | 2.9x |
| 100（全部模块） | 5 855 | **4.8x** |

提示词变长不只是慢 —— **工具越多，模型选错的概率越高**。

### 好在小6 已经有"两级筛选"的第一级

```
用户消息
   ↓
① context_builder._TOOL_HINTS（34 个关键词粗筛）
   不像要动手 → 连 tool_caller 都不进（省一次云端往返）
   ↓
② tool_caller._llm_decide（LLM 在工具表里选）
```

**方案：给每条能力声明 `hints`，让第一级粗筛把候选缩到 ~15 个再交给 LLM。**

```python
{"name": "stats_report", "desc": "用量统计", "hints": ["统计", "报表", "用量", "多少条"]}
{"name": "memory_organize", "desc": "整理记忆", "hints": ["整理记忆", "合并记忆", "记忆乱"]}
```

于是：

```
100 条能力 → 关键词命中 ~5~15 条 → 进 LLM 提示词只有这些
→ 提示词稳定在 ~1.5k 字符（而不是 5.8k）
→ 模型选择准确率不下降
```

**兜底**：关键词全不命中时，用一个小 `always` 集合（约 10 个通用工具）——
保证"没想到关键词"也能用。

## 六、落地的四个机制（v3 补全）

### ① 双来源能力注册表

```
来源A 插件模块（48）: 模块声明 TOOLS → rebuild 写进 manifest.tools → RSA 签名
来源B core 模块（24）: core/core_caps.py 集中声明
                              ↓
              core/module_caps.py 合并（照 module_buttons.py 的 75 行结构）
                              ↓
              tool_caller 接入（含 hints 两级筛选）
```

### ② 统一分发器（v3 新增，修阻塞）

按签名决定 `kwargs` / `first-arg`，**向后兼容现有 19 个工具**。

### ③ 命令面板 Ctrl+K

数据源 = `module_caps.load_tools()`；带参数的能力**内联追问**。
`gui/module_tools_dialog.py` **已有搜索框**，升级即可。

### ④ 两个预算守卫（**这是"落地"的关键**）

| 守卫 | 管什么 | 超了会怎样 |
|---|---|---|
| `tools/check_buttons.py` | GUI 控件数 ≤ 60 | 提交前拦住 |
| `tools/check_tools.py` | `_llm_decide` 提示词 ≤ 2 000 字符 | 提示"加能力请声明 hints" |

**没有守卫的话，减完几个月又会有人"顺手加个按钮"长回去。**
