## 〇、结论速览（30 秒版）

核心一句话：
    **改代码 ≠ 提交(commit) ≠ 推送(push) ≠ 合并(merge)。**
    四件事互不绑定，日常开发只做前两件里的"本地部分"。

直接回答四个高频问题：

  Q1 每次改代码都要上传远程 GitHub 吗？
     → 不要。改、测、看都在本地，跟远程无关。

  Q2 每次改代码都要提交(commit)吗？
     → 不强制。想留"回退点"就 commit，频率自定，可攒多次再提交。

  Q3 每次提交都要推送(push)到远程吗？
     → 不必。commit 只在本机；一个完整功能做完才 push。

  Q4 每次推送都要合并(merge)吗？
     → 不必。只有"这批要成为正式版本、进 main"才合并，且走 PR。

默认节奏（照做即可）：
    本地改 → 测试通过 → 本地 commit（多改几处攒一起）
    → ……（反复本地迭代，不碰远程）
    → 一个完整功能做完 → push 到远程 + 开 PR + 等 CI 绿 + 合并进 main。

## 一、Git 的四个运作区域（先搞懂"改的东西存在哪"）

你的改动，按"流向"要经过 4 个区，理解这个，后面全通：

  ① 工作区（Working Directory）
     · 位置：E:\xiaoliu 下的真实文件，你正在编辑的东西。
     · 改了不保存/不 add，就只在这。git 还不知道（或知道但未记录）。

  ② 暂存区（Staging Area / Index）
     · 位置：本机内存 + .git/index。
     · 命令：git add <文件>  —— 把工作区改动"标记为准备提交"。
     · 作用：让你挑"哪几个文件的改动进入下一次 commit"。

  ③ 本地仓库（Local Repository）
     · 位置：E:\xiaoliu\.git（你本机）。
     · 命令：git commit —— 把暂存区内容存成一个快照（有历史、可回退）。
     · 到这里为止，全程没联网。

  ④ 远程仓库（Remote Repository）
     · 位置：github.com/jiek860/xiaoliu-app（origin）。
     · 命令：git push —— 把本地 commit 上传到远程。
     · 到这里才联网，才有备份 / 协作 / 触发 CI 的意义。

关键认识：
    ①②③ 都在你本机，随便玩，零网络。
    ④   涉及网络，属于"对外动作"，才需要考虑频率。

## 二、五个核心动作逐个拆解

1. git add（暂存）
   · 作用：把工作区改动送进暂存区，挑选本次要提交的内容。
   · 常用：
        git add <文件>      # 只加指定文件
        git add -A / add .  # 加全部改动（含删除）
   · 底线：不 add 就无法 commit；add 本身不改变任何历史。

2. git commit（提交）
   · 作用：把暂存区拍成本地快照，写进历史。
   · 联网：否。
   · 频率：自定。可一点一 commit，也可攒两天一次。
   · 触发：pre-commit 快检（约 5 秒），见第六节。

3. git push（推送）
   · 作用：把本地已有的 commit 上传到远程同名分支。
   · 联网：是。
   · 频率：一个完整功能做完再做，不必跟每次 commit。
   · 触发：pre-push 全检（约 90 秒），见第六节。
   · 注意：本项目一般不直接 push main（main 有保护），
           工程上也不直接用 push 发布——用发布脚本走 PR（见第四节）。

4. git fetch / git pull（拉取）
   · fetch：只把远程最新进度拉到本地引用，不改你的工作区。
   · pull ：fetch + merge（把远程并进当前分支），会改工作区。
   · 用途：同步别人/其它机器推上来的 commit；对齐"本地 vs 线上"。
   · 本项目因为 github.com:443 不稳，fetch 可能失败重试即可。

5. git merge / GitHub 合并 PR
   · 作用：把一条分支的改动并进另一条（本项目是并进 main）。
   · 本项目 main 走 GitHub 的 Pull Request 合并，发布脚本自动 squash。
   · 频率：只在"正式发版"时做。

三句话记法：
    add 是整理，commit 是本地存档，push 是上传存档，merge 是发布存档。
    只有 push 和 merge 才需要网络，也只有它们才谈得上"上传远程"。

## 三、决策树：这次改动到底要不要提交 / 推送 / 合并

拿到一次改动，按下面顺序问自己：

  第 1 问：这段改动"成型"了吗（能编译、能跑、逻辑完整）？
     ├─ 没成型 / 还在试 → 留在工作区，什么都不做（连 add 都可以不做）
     └─ 成型了 → 继续第 2 问

  第 2 问：我想留一个"能回退到此刻"的存档点吗？
     ├─ 无所谓 / 马上还要大改 → 可不 commit（继续写，不会丢，只是没存档）
     └─ 想要存档点 / 想切分支 / 想暂存半成品 → git commit（本地，快检 5 秒）

  第 3 问：这是一个"完整可交付的功能/修复/批次"了吗？
     ├─ 不是，还有后续 → 停在本地 commit 即可，**不要 push**
     └─ 是 → 继续第 4 问

  第 4 问：要不要让这个版本"离开本机"（备份／换机器写／发版）？
     ├─ 只是备份或换机器写 → git push 到一条你自己/功能分支（不是 main）
     ├─ 要成为正式版本 v25.x.x → 走发布脚本：推功能分支 + 开 PR + 合并进 main
     └─ 都不用 → 继续留在本地，什么时候想推再推

决策速记：
    没成型  → 什么都不做
    成型了  → commit（可选，本地）
    完整了  → push（可选，要备份/协作时）
    发版了  → merge（唯一会改 main 的动作）

## 四、本项目特有的发布链路（为什么不用 git push）

背景：本机直连 github.com:443 常被 RST（连接重置），但
      api.github.com 稳定可用。因此**发布不走 git push**，而是固化脚本：

    py -3 tools\github_api_push.py --message-file 说明.txt `
        --pr-title "标题" --wait-ci --merge

脚本流程（全程只访问 https://api.github.com）：
    1. 读工作区/指定文件改动，按原始字节上传（不转行尾）；
    2. 内容没变的文件复用远端 blob（不重复上传，省时）；
    3. 把改动包成功能分支（如 x6/batch31-...）提交上去；
    4. 创建 Pull Request（PR）；
    5. --wait-ci：轮询该 commit 的 check-runs，直到 全部通过；
    6. --merge：CI 全绿后自动 squash 合并进 main。

硬性规则：
    · main 有分支保护，**严禁直接 git push 到 main**；
    · 合并固定 squash：一支分支的一堆 commit 会被压成 m 主线上 1 个干净提交；
    · 发布脚本只在"发版"时用，日常本地开发完全不碰它。

常用参数（完整见脚本内 docstring）：
    --branch NAME      目标分支（默认 x6/auto-<时间戳>）
    --base NAME        基分支（默认 main）
    --message-file     提交说明文件（UTF-8）
    --pr-title / --pr-body    PR 标题 / 正文
    --wait-ci / --ci-timeout  轮询 CI（默认 1800 秒）
    --merge / --merge-method  拍 CI 绿后合并（默认 squash）
    --files A B       只上传指定文件（默认取 git status 改动）
    --dry-run         只打印计划，不发写请求

## 五、分支策略与命名规范

当前分支分类（git branch -a 现状）：

  分 类      命名                        用途                        何时并进 main
  ─────────────────────────────────────────────────────────────────────────────
  main        main                       唯一正式主线，受保护           —
  功能批次    x6/batch<N>-<主题>-<日期>   按批次开发（如 batch31）       批次验收通过后
  功能分支    feat/<主题>                 单功能开发                    功能完成、评审后
  修复分支    fix/<主题>                  修 bug                       修好、测试通过后
  文档分支    docs/<主题>                 纯文档改动                    核对后
  杂项分支    chore/<主题>                依赖/清理等杂活               核对后
  旧分支      backup/*, release/*, etc.   历史归档，多数已合并或废止    不再动

规则：
    1. 永远在**自己的分支**上开发，不要直接在 main 上改；
    2. 一个分支做**一件事**（一个功能/一次修复/一批文档）；
    3. 分支名用短横线连小写英文（批量加日期后缀如 -20261030）；
    4. 合并进 main 统一走 PR + squash；
    5. 用完就删的分支，合并后可清理，避免分支列表越积越多。

## 六、两档门禁详解（提交前 / 推送前各跑什么）

git hook 目录：E:\xiaoliu\.githooks\（通过 core.hooksPath 生效）。
两档分法：commit 是本地动作、要快；push 是对外动作、要稳。

  ◆ 第一档 pre-commit（提交前，约 5 秒，跑快检）
     触发时机：git commit（自动）
     手动跑：   py -3 tools\pre_commit_check.py
     跳过：     git commit --no-verify（请说明理由）
     包含 6 项：
       1) 语法检查        compileall 一遍 core/gui/modules/... 
       2) 版本号一致性    tools/check_version.py
       3) 按钮预算        tools/check_buttons.py
       4) 工具/提示词预算 tools/check_tools.py
       5) 线程安全        tools/check_threads.py
       6) 静默失败棘轮    tools/check_silent.py

  ◆ 第二档 pre-push（推送前，约 90 秒，跑全检 = 上 6 项 + 3 项慢的）
     触发时机：git push（自动）
     手动跑：   py -3 tools\pre_commit_check.py --full
     跳过：     git push --no-verify
     额外 3 项（慢的/对外的）：
       7) 结构契约        tools/check_shapes.py（要加载 76 个模块，约 12 秒）
       8) 插件仓库一致性  tools/check_repo_sync.py（modules_repo 会推 gitee，用户端拉它装插件）
       9) 全部用例        pytest tests/ -q（约 70 秒）

含义（重要，理解它你就不怕提交了）：
    · commit 只拦"明显不该提交的"，很快、不烦人 → **频繁 commit 几乎零成本**；
    · push 才把慢的、对外的全跑一遍 → **对外动作值得多花一分半确认**。

其它常跑的门禁（CI 里也会自动跑，本地按需手动）：
    tools/check_file_sizes.py          单文件 <600 行守卫
    tools/check_feature_freeze.py      冻结守卫（见第九节）
    tools/check_coverage_thresholds.py 覆盖率门槛（总 ≥60，core≥57，gui≥40）
    tools/check_diff_coverage.py       改动行覆盖率 ≥70
    tools/check_plugin_api.py          插件 API 一致性
    tools/check_plugin_repo.py         插件公共仓库验签/清单
    tools/audit_signals.py             Qt 信号"有 emit 无 connect"审计

## 七、提交信息（commit message）书写规范

本项目提交信息用「类型前缀 + 一句话」，跟 git log 历史一致：

  类型前缀   含义                           示例
  ─────────────────────────────────────────────────────────────
  feat       新功能                        feat: 新增聊天话题时间线
  fix        修 bug                        fix: 修正 CI 静态检查(rF811)
  docs       纯文档                        docs: 补全架构速览与检测手册
  chore      杂活(依赖/清理/配置)           chore: 升级依赖并清理缓存
  refactor   重构(不改行为)                 refactor: 抽取公共校验函数
  test       只动测试                      test: 补 coverage 单元测试
  revert     回滚                          revert: 回退上次合并

书写要点：
    1. 首行：类型: 一句能看懂的话（中文即可，简短）；
    2. 需要时再空一行补正文，逐条列"为什么改 / 改了啥 / 验证结果"；
    3. 一次 commit 只做一类事，不要 feat 和 fix 混在一起；
    4. 提交信息里**不要出现 BOM 字符**（PowerShell 写中文易带入，会导致
       GitHub API 创建 tree 报 422），用 UTF-8 无 BOM。

示例（完整）：
    fix: 修正工作台问题面板 items() 遍历

    - 遍历 dict items() 时 key 未使用，ruff B007 报错
    - 改为遍历 values()，行为不变
    - 验证：ruff 通过；test_workbench_problems 13 passed

## 八、版本号与发版流程

版本号权威来源：core/version.py 的 __version__（现在是 v25.5.0）。
历史上 CHANGELOG 和 version.py 长期不同步，已有 check_version.py 兜着。

发版步骤（要发布时才做，日常开发不做）：

  1. 改 core/version.py 的 __version__ 与 __build_date__（唯一权威源）；
  2. 在 CHANGELOG.md 顶部加一条新版本条目（注明日期与改动清单）；
  3. 跑 py -3 tools\check_version.py
        —— 会把 CHANGELOG、分发说明、示例等逐处核对；
        —— 不一致就列出来并返回非零；--fix 能自动改的自动改；
  4. 更新文档（docs/README.md 日期/版本、docs/00、使用说明等）；
  5. 更新程序内教程 gui/tutorial_dialog.py（若涉及用户可见行为）；
  6. 本地全检 py -3 tools\pre_commit_check.py --full；
  7. 走发布脚本推分支 + PR + 等 CI + 合并（见第四节）。

版本规则：
    · 只改 core/version.py，然后让 check_version.py 帮你找遗漏；
    · 不要只改 CHANGELOG 漏改 version.py（这是历史坑）。

## 九、冻结守卫与解冻期

tools/freeze_baseline.json 记录一批"只许降不许升"的基线：
    · Feature 数（46）
    · core / gui / 测试 文件数
    · 按钮总数（60）
    · 覆盖率门槛（总 60%、core 57%、gui 40% 等）
    · active 开关：true=冻结中（逐项拦截），false=解冻期（只读基线）

当前状态（2026-10-30）：active = false —— 处于解冻期（批次 31）。

含义（跟提交规则的关系）：
    · 解冻期加新文件/新按钮不会被 freeze 守卫拦（但仍受其它门禁约束）；
    · 解冻有期限（freeze_until），批次收尾要 --init --force 重建基线并置 active=true；
    · 无论冻结与否，按钮预算、文件行数、覆盖率这些"硬门禁"都照常生效。

每次提交时若 pre-commit 报了 freeze 相关错误，去查 docs/106_解冻与预算决策_2026-10-30.md，
按预算上限判断该不该加，而不是盲目 --no-verify。

## 十、常见场景决策表（照表查）

  场景                                    动作                               动远程吗
  ──────────────────────────────────────────────────────────────────────────────
  刚改几行，还在试                  什么都不做，留工作区                    否
  改到一半想切分支                   git add + commit 暂存半成品              否
  改完一个小修复                     commit（本地，快检 5 秒）                否
  攒了几个 commit，还没做完功能      留在本地，不 push                       否
  一个完整功能做完，想本地留档        commit（本地）                         否
  一个完整功能做完，想备份/换机       push 到功能分支                        是(push)
  一个完整功能做完，要发版            push + PR + 合并进 main                 是(push+merge)
  想同步别人推上来的改动             git fetch / pull                       是(fetch)
  纯文档改了几处                    commit（本地）即可，可攒到发版一起       否
  文档改动需要进主线                 走 docs/<主题> 分支 + PR                 是(merge)

通用结论：只有"备份/协作/发版"这三类真实需求才需要 push；
         只有"发版"才需要 merge。

## 十一、常见误区 Q&A

Q1：不 commit，改半天的代码会丢吗？
A：不会"自动丢"。不 commit 只是没有快照，出问题不能回退到该点。
    改到重要节点建议 commit 一下图安心（本地 5 秒，几乎无成本）。

Q2：commit 了就必须 push 吗？
A：不必。commit 只在本机。commit 100 次不 push 也没人管，远程纹丝不动。

Q3：push 了就必须马上 merge 吗？
A：不必。push 出去只是备份/给 CI 看；要不要并进 main 由你决定，放几天也行。

Q4：能直接改 main、直接 push main 吗？
A：本项目不可以。main 有分支保护，必须走 PR，由发布脚本代劳。

Q5：push 被 pre-push 全检拦住了怎么办？
A：说明测试没过或结构/插件仓库不一致，按提示改完再 push；
    确认真无碍才用 git push --no-verify（要能讲清理由）。

Q6：发布脚本和 git push 什么关系？
A：因 github.com:443 直连不稳，脚本改走 api.github.com 完成
    "建分支→提交→开 PR→等 CI→合并"整套流程。日常开发用不到它。

Q7：本地和线上对不齐了怎么办？
A：git fetch origin --prune，需要时 git reset --hard origin/main 对齐本地 main；
    但 reset --hard 会丢本地未提交改动，先确认工作区干净或已 commit。

Q8：提交信息中文被加 BOM 了会怎样？
A：会导致 GitHub API 建 tree 报 422 "tree.path cannot start with a slash"。
    用 UTF-8 无 BOM 保存提交信息文件即可。

Q9：CRLF/LF 换行不一致有影响吗？
A：会误报文件"跟 modules/installed 不一致"。源码统一 LF；
    仓库级 core.autocrlf 已设为 false，避免本地拉取时转行尾造成假 diff。

## 十二、速查便签（贴桌子用）

    ┌─────────────────────────────────────────────────────┐
    │  改代码 ≠ commit ≠ push ≠ merge                     │
    │                                                     │
    │  改代码  随时，本地，免费，随便改                     │
    │  add     网上好了，整理暂存                          │
    │  commit  想留档就做，本地 5 秒，多攒不亏              │

    │  merge   要发版才做，走 PR 进 main，squash            │
    │                                                     │
    │  日常：本地改、本地 commit，随便攒。                 │

## 十三、文档分类与合并规则（写文档前必读）

背景：docs/ 以前有 43 个零散 md/txt，方案、报告、单批次记录越堆越多，
同类内容散在多处，找不到也维护不动。2026-10-30 已合并为
**10 个主题合订本 + 2 个运行时 txt + 1 个索引（README.md）**。

### 13.1 十个合订本（新内容只能往这里加）

    00  产品架构与UI主文档          产品定位/架构/UI/工作台/模块全景/开源对标
    10  开发流程与工程手册          流程/发版/CI/备份/拆分记录/流程变更
    20  优化路线与实施记录          各批次落地过程、问题修复记录
    30  模块规则与API参考           能力/API/智能体手册/插件标准与审计
    40  安全加固与权限说明          安全架构、加固、权限模型
    70  兼容性与数据迁移            兼容矩阵、数据迁移、插件 API 边界
    80  质量检测与发布门禁          检测报告、验收、CI/发布门禁
    92  Agent回归基线               回归样本、SWE-bench、评测基线
    101 功能深化方案与批次计划       规划、拟人聊天、批次计划、开关与解冻决策
    109 开发规则与提交发布          本文件（规则类，不再并入别处）

### 13.2 新文档的处理流程（强制）

    第 1 步  判断归属：对照 13.1 找到最接近的主题；
    第 2 步  属于某类 → 追加到该合订本末尾，格式统一为：
                 ## 附录：<主题>（<YYYY-MM-DD>）
                 正文……
              并在该合订本头部「合并来源」一行补上主题名；
    第 3 步  只有同时满足以下三种情况，才允许新建独立文件：
                 a) 程序运行时读取（如用户协议、隐私政策、模块星图）
                 b) 需要独立发布 / 跨仓库分发（如插件标准对外单页）
                 c) 需要独立签名或校验
    第 4 步  确需新建 → 编号取所属类别的下一个号段，并在 docs/README.md 登记；
    第 5 步  同步更新 docs/README.md 的「更新日期」与对应「维护要求」。

### 13.3 硬性禁止

    ✗ 在 docs/ 根下新建一次性方案 / 临时报告 / 单批次记录；
    ✗ 同一个主题拆成多个文件（多文件版本会漂移，必然对不上）；
    ✗ 删除合订本里的附录（附录是历史证据，只增不删）；
    ✗ 新增文档后不改 README 索引（等于没登记，后续找不到）。

### 13.4 与提交规则的关系

    文档改动同样遵循第三章决策树：
      日常：本地改 + 本地 commit（可攒批）；
      完整交付：push 到 docs/<主题> 分支；
      进主线：走 PR + squash 合并（发布脚本代劳）。
    文档合并属于"完整交付"，做完应跑：
      py -3 -m pytest tests/test_docs_consistency.py tests/test_user_docs_intact.py -q
      py -3 tools/check_version.py
