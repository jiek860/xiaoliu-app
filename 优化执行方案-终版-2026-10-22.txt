第十二部分  三个工程注意事项（补充）

--------------------------------------------------------------------------------
[注意 1] mcp_catalog 维护成本
--------------------------------------------------------------------------------
  问题：data/mcp_catalog.json 写死 20~30 个 MCP server 包名/参数，
        半年后可能全失效（包改名、参数变、服务下线）。

  解决方案：
  1. catalog 里每条加 "last_verified" 字段（ISO 日期）
  2. tools/check_mcp_catalog.py：每月自动 ping 一次 catalog 里的 server，
     失效的自动标记 "broken": true，UI 里灰掉
  3. 每季度人工过一次：把 broken 的下架，加新的
  4. UI 上加"我要上报失效"按钮：用户点一下就记录到 data/mcp_broken.json

--------------------------------------------------------------------------------
[注意 2] SWE-bench 资源约束
--------------------------------------------------------------------------------
  问题：全量 SWE-bench lite 要下载仓库 + 装依赖，单次几十 GB 磁盘/网络。

  解决方案：
  1. 只跑本地小样本（20 题），不全量
  2. 每题独立目录 tests/eval/swe_bench/cases/，跑完即删
  3. 用 Docker 容器隔离（P1-5 做完后复用），不污染主环境
  4. 基准回归只在本地手动跑，不进 CI（CI 只跑单元测试）
  5. 输出存 docs/benchmarks/ 下的 markdown，不存大文件

--------------------------------------------------------------------------------
[注意 3] Feature Flag（功能开关）
--------------------------------------------------------------------------------
  问题：P0/P1/P2 新功能上线后，如果有 bug，用户没法关掉。

  解决方案：
  1. core/feature_flags.py：一个简单的 dict，读 data/flags.json
  2. 默认全部开启；用户可以在设置里关掉某个功能
  3. 每个新 Feature 登记时自动加一个 flag：
       flags = {"deep_research": True, "coder_pro": False, ...}
  4. 新功能默认 True，但 coder_pro / browser_agent 这种危险的默认 False
  5. Feature 可见性检查时先看 flag：flag=False 就不显示入口
  6. 回滚成本：改 flags.json 一行就关了，不用发版
