【1.1 确认 Python 环境】
命令：python --version（或 py -3 --version）
预期：Python 3.10.x / 3.11.x / 3.12.x
异常：3.9 及以下不支持；3.13 未验证；Windows 7/8 不建议。

【1.2 确认依赖】
命令：pip list | findstr "PyQt5 requests cryptography"
预期：三个都有。
异常：缺则 pip install PyQt5 requests cryptography

【1.3 确认 Ollama】
命令：ollama list
预期：列出已下载模型。
异常：没有则先 ollama pull qwen2.5:7b

【1.4 确认数据目录】
路径：E:\xiaoliu\data
预期：有 config.json、chats.db、logs/；正常迁移后还有 _schema.json、_migrations/
异常：第一次启动会自动创建；旧数据会先备份再按 v0->v1->v2 迁移。

【1.5 运行兼容矩阵检查（开发者/发布）】
命令：py -3 tools\check_runtime_compat.py --allow-server
预期：Python 3.10/3.11/3.12、Windows 10/11，必需依赖齐全。
异常：版本不在支持范围或缺少 PyQt5/requests/numpy/cryptography/psutil。

【1.6 数据迁移预演（开发者/发布）】
命令：py -3 tools\migrate_data.py --dry-run --json
预期：migrated/skipped/errors 结构清晰，不修改原文件。
异常：查看 errors，先备份 data/，不要直接删除。

【1.7 插件 API 边界检查（开发者/发布）】
命令：py -3 tools\check_plugin_api.py
预期：api_version=1.0，checked=42，failed=[]。
异常：重新 rebuild_modules_repo.py --apply -> sign_modules.py；
      第三方插件不能 import core 私有模块。

║ 第九部分：为什么要分方法检测                            ║
╚══════════════════════════════════════════════════════════╝
任何一个 BUG 都不是凭空出现，而是某个维度上不一致。
程序有十几个维度：参数、类型、状态复位、数据对齐、并发、命名、相似实现同步等。
一次通读只能看到一两个维度。轮换 7 种方法，就能一轮比一轮深入。
关键认知：
“又发现了新 BUG” ≠ “程序里新增了 BUG”
“又发现了新 BUG” = “这次又看到了一层”
就像体检：抽血、CT、核磁各查一遍，不是身体又变差，而是又看到一层。

╔══════════════════════════════════════════════════════════╗
║ 第十部分：调用链一致性核对                              ║
╚══════════════════════════════════════════════════════════╝
目的：找 A 调用 B 的用法 与 B 定义的接口之间的不匹配。
步骤：
1. 打开 A 文件，记下所有调外部方法：obj.method(...)、trunk.call("模块","方法",...)
2. 打开被调用方定义文件，找到方法原文。
3. 对比：参数个数、关键字参数名、是否有不认识的 kwargs、返回值类型。
4. 特别关注：下划线差异（_save_config vs save_config）、命名习惯（save/backup/write）。
能抓：调用不存在的方法、参数拼错、返回值类型误用。
示例：
调用 gui/settings_dialog.py 的 trunk._save_config()，但 core/trunk.py 只有 save_config → AttributeError。
调用 memory_cards.maybe_summarize(...)，但对方无返回值 → 条件永不成立。
盲区：必须 A、B 两个文件都打开；文件多可能漏；动态方法名静态对不出。
适用：core/trunk.py 的 call()、所有 trunk.call、所有少见 obj.method()。

╔══════════════════════════════════════════════════════════╗
║ 第十一部分：数据结构对齐检查                            ║
╚══════════════════════════════════════════════════════════╝
目的：找同一数据对象在不同位置“结构假设”不一致。
步骤：
1. 列出关键数据结构：self.data、self.embeddings、self._emb_mat、self.memory、self.module_meta、due_review() 返回值。
2. 对每个结构回答：正确类型？必须和谁等长/同步？谁更新？谁读取？
3. 找所有更新点，看关联结构是否同步更新。
4. 找所有读取点，看是否按正确类型消费。
能抓：dict 当 list 切片、索引偏移、长度不同步、相似度公式错。
示例：
_emb_mat 与 data 长度必须相等，但 _add_locked 只更新 data 和 embeddings → 搜索退化慢路径。
Jaccard 写成 len(new & oldf)/max(...) → 实际是重叠系数。
due 是 dict，却 for item in (due or [])[:5] → TypeError。
盲区：结构隔得远易漏；动态构造需跑一遍。
适用：core/vector_store.py、core/knowledge_graph.py、core/trunk.py memory、forgetting_curve.py、memory_loop.py。

╔══════════════════════════════════════════════════════════╗
║ 第十二部分：状态复位路径穷举                            ║
╚══════════════════════════════════════════════════════════╝
目的：找状态置位后，某些代码路径跳过复位。此类 BUG 不会立刻报错，但会让程序永久异常。
步骤：
1. 搜置位：self._xxx = True、self._flag = 1、self._lock.acquire()、self._state = "运行中"。
2. 对每个状态变量列：谁置位？谁复位？复位在函数哪个位置？
3. 检查：提前 return、raise、break/continue、条件分支跳过复位。
4. 结论：复位在 finally 里安全；复位在函数末尾，只要提前 return 就漏。
能抓：try/finally 缺失、提前 return 资源未释放、死锁/永久阻塞。
示例：
_chat_in_progress = True，但电脑控制命中后 return，走不到末尾 → 永远 True。
正确写法：
def reply(...):
    try:
        self._chat_in_progress = True
        return self._reply_inner(...)
    finally:
        self._chat_in_progress = False
        self._chat_active_until = time.time() + 120
适用：core/trunk.py、core/llm_client.py、core/vector_store.py、所有持锁释放锁处。

╔══════════════════════════════════════════════════════════╗
║ 第十三部分：跨文件类型传递追踪                          ║
╚══════════════════════════════════════════════════════════╝
目的：找 A 传给 B 的值，B 按错误结构消费。
步骤：
1. 找数据流：产生点 → 传输点 → 消费点。
2. 每段问：这时它是什么类型？
3. 特别关注：dict key 名、list 元素类型、字符串编码、时间戳是 str 还是 float。
4. 逐段检查消费方是否按正确假设使用。
能抓：key 名拼错、类型不匹配、结构假设错误、时间戳混用。
示例：
先更新 last_active 再计算 hours → hours≈0，if hours>24 永远 False。
method 配置为 "chat" 无点，却 t["method"].split(".") → ValueError。
存储 "time" 为字符串，消费时 time.time() - m.get("time",0) → TypeError。
盲区：链路长、中间变形多次；配置定义需打开配置对照。
适用：core/trunk.py 与模块之间、core/pipeline/* 与 trunk、modules/installed/* 与 core/*。

╔══════════════════════════════════════════════════════════╗
║ 第十四部分：命名 / 属性存在性核对                        ║
╚══════════════════════════════════════════════════════════╝
目的：找用了不存在的方法/属性，或旧名字没改全。
步骤：
1. 打开一个类，列出全部成员：__init__ 里 self.xxx、def method。
2. 找该类所有使用点。
3. 逐个核对：obj.xxx 存在吗？obj.method(...) 存在吗？
4. 特别注意：大小写、下划线一个还是两个、命名习惯改动后是否全局替换。
能抓：属性拼写错误、方法未定义、旧名字未改全、定义了没使用。
示例：
trunk._save_config()，但 Trunk 只有 save_config。
HARD_KW 定义但从未使用。
调 group_parallel.compose()，实际有 compose 的是 group_chat。
工具：grep -r "_save_config" .
适用：每个类的使用点 vs 定义点，尤其 core/trunk.py、core/llm_client.py。

╔══════════════════════════════════════════════════════════╗
║ 第十五部分：并发与时序推演                              ║
╚══════════════════════════════════════════════════════════╝
目的：找多线程共享数据上的竞态、脏读、文件损坏。
步骤：
1. 找多线程入口：threading.Thread、_bg、scheduler、learning_loop、_auto_unload_loop。
2. 找被这些线程读写的共享变量/文件：self.modules、self.memory、self.module_meta、self.data、self.embeddings、data/*.json。
3. 对每个共享对象问：有锁吗？锁范围够吗？文件写原子吗？
4. 特别关注连续发消息：会不会同时起多个 _bg？会不会同时写同一文件？
能抓：数据竞争、脏读脏写、文件损坏、半截文件。
示例：
mem_add 从多个 _bg 调用，self.memory[uname] 无锁修改，save_memory 非原子写 → 数据丢失+文件损坏。
_bg 无并发限制，连续 5 条消息起 5 个线程，每个可能写 graph.json → 竞态。
_emb_mat 长度 > data，广播失败。
正确写法：
加锁 self._mem_lock = threading.Lock()
原子写：tmp = path + ".tmp"; json.dump(...); os.replace(tmp, path)
适用：core/trunk.py、core/vector_store.py、core/knowledge_graph.py、scheduler.py、learning_loop.py。

╔══════════════════════════════════════════════════════════╗
║ 第十六部分：同类对比 / 模式识别                          ║
╚══════════════════════════════════════════════════════════╝
目的：找两个相似实现中一个改了另一个忘了改。
步骤：
1. 找功能相似的实现对：core/plugin_market.py vs modules/installed/plugin_market.py、llm_client 内部方法、同类模块。
2. 逐行对比：A 有的方法 B 有没有？同样功能实现一致吗？
3. 找类似模式：打开文件写是否都用原子写？调 LLM 是否都有超时？有 try 是否都有 finally？
4. 反查：从日志报错回溯代码；从用户反馈现象回溯代码。
能抓：一个版本改了另一个忘改、规范不统一、遗漏方法。
示例：
core/plugin_market.py 有 _load_meta/_save_meta，modules/installed/plugin_market.py 没有，但加载的是后者 → module_meta 不持久化。
Trunk.save_config 原子写，core/config.save_config 不原子 → reset_config 中途崩损坏配置。
save_* 原子性不齐：save_config 原子，save_memory/save_kb/knowledge_graph._save 不原子，vector_store.save 原子。
盲区：需要有“两个相似实现”才能对比。
适用：所有双实现模块、所有 save_*、所有 open(..., "w")。
